# **Методология Agent Harness (Harness Engineering)**

## **Полное техническое руководство по проектированию и интеграции надёжных AI-агентов**

## **1\. Введение в концепцию**

Традиционный подход к автоматизации задач с помощью LLM (когда модель получает текстовое описание задачи и сразу генерирует финальный код или артефакт) демонстрирует крайне низкую стабильность в реальных производственных условиях. Основные проблемы такого подхода («свободного чата»):

* **Потеря контекста:** В процессе длинных диалогов или при обработке крупных файлов модель теряет фокус на изначальных требованиях.  
* **Хаотичная архитектура:** Прямой прыжок от постановки задачи к написанию кода приводит к нарушению архитектурных слоев, игнорированию ограничений безопасности и упущению пограничных случаев (*edge cases*).  
* **Отсутствие валидации:** Ответ модели принимается на веру без автоматической проверки его синтаксической и логической корректности.

**Agent Harness (Инженерный контур валидации)** — это концепция встраивания ИИ-модели в жестко управляемый программный контур (фреймворк оркестрации, такой как Agentweaver). Модель больше не принимает самостоятельных решений о логике переходов между этапами. Она становится исполнителем внутри изолированных шагов пайплайна, где каждый промежуточный результат переводится в машиночитаемый артефакт и подвергается каскадной автоматической проверке (*Quality Gates*) и исправлению через циклы обратной связи (*Feedback Loops*).

## **2\. Базовые архитектурные принципы контура**

Чтобы ИИ-агент функционировал как надежная инженерная система, его программная обвязка должна строго следовать пяти фундаментальным принципам:

1. **Машиночитаемые раздельные артефакты:** Данные между этапами передаются не в виде сырого лога переписки, а фиксируются в структурированных файлах. Для модели генерируются строгие схемы в формате JSON, а для человека-оператора параллельно создается документация в формате Markdown (.md).  
2. **Точки контроля качества (Quality Gates / Guard Rails):** Каждый этап пайплайна отделен от следующего логическим шлюзом валидации. Если текущие метрики или результаты тестов не соответствуют требованиям, контур блокирует продвижение задачи дальше.  
3. **Встроенные циклы самоисправления (Feedback Loops):** Обнаружение ошибок внешними инструментами (компиляторами, линтерами, тест-ранерами) не прерывает выполнение процесса аварийно. Контур автоматически перехватывает логи ошибок, форматирует их в новый системный промпт и возвращает модель в фазу исправления (Fix Loop).  
4. **Интеграция с внешним окружением (Tool Use):** Оркестратор обладает полномочиями выполнять системные вызовы: обращаться к API таск-трекеров, считывать и записывать файлы в локальной ОС, запускать консольные утилиты проверки кода и управлять ветками Git.  
5. **Наблюдаемость и детерминированность (Observability):** Состояние пайплайна должно быть прозрачным на каждом шаге. Система логирует текущую фазу, промежуточные артефакты, количество итераций в циклах исправления и причины отказов.

## **4\. Спецификация слоев архитектуры под ИИ-агента**

Для программной реализации данного контура кодовая база вашего оркестратора должна быть разделена на 4 изолированных слоя:

### **А. Слой управления контекстом (Context & Artifact Layer)**

Отвечает за сбор и хранение данных. При инициализации создается скрытая или изолированная директория внутри проекта (например, .agent\_weaver/). В ней создаются подкаталоги:

* context/ — сырые выгрузки из внешних систем.  
* blueprints/ — сгенерированные ИИ схемы планов и архитектурных концепций в формате JSON.  
* feedback/ — логи ошибок сборщиков и линтеров.

### **Б. Слой вычислительных агентов (LLM Core / Ролевая модель)**

Контур не использует один общий контекст для ИИ. На каждом этапе оркестратор переключает **системный промпт (System Prompt)**, изолируя модель в рамках конкретной роли:

1. **Агент-Архитектор (Role: Architect):** Принимает бизнес-требования ![][image1] формирует технический проект изменений системы, декомпозирует задачу на мелкие модули.  
2. **Агент-Программист (Role: Developer):** Принимает технический проект изменений ![][image1] пишет чистый код, не отвлекаясь на обсуждение требований.  
3. **Агент-Критик/Ревьюер (Role: Code Reviewer):** Принимает изначальный план \+ получившийся дифференциал кода ![][image1] ищет логические и архитектурные дефекты, выступая в роли строгого цензора.

### **В. Слой инструментов и валидации (Tooling & Integration Layer)**

Этот слой представляет собой программные методы на основном языке оркестратора (Python/Node.js/Go), выполняющие команды операционной системы и интеграцию через API:

* **Jira/GitHub Client:** Выгрузка полей Title, Description, Acceptance Criteria, Comments.  
* **Subprocess Runner:** Запуск консольных утилит (например, golangci-lint run ./..., pytest \-v, npm run test) с обязательным перехватом кодов возврата (Exit Code) и потоков ошибок (stderr/stdout).

### **Г. Слой маршрутизации и конечных автоматов (State Machine & Feedback Layer)**

Управляет логикой переходов. Внутри слоя зашиты правила:

* Если Exit Code \== 0, сменить состояние пайплайна на следующее по списку.  
* Если Exit Code \!= 0, инкрементировать счетчик попыток fix\_attempts, вызвать метод отката состояния кода (git checkout), передать управление Агенту-Программисту вместе с логом ошибки.  
* **Предохранитель (Max Retries Limit):** Если fix\_attempts \> 3, остановить пайплайн, отправить алерт человеку-оператору. Это предотвращает бесконечный цикл и избыточное расходование токенов LLM при неразрешимых конфликтах в коде.

## **5\. Детальная пошаговая инструкция реализации workflow**

### **Этап 1: Импорт задачи и входной контроль качества (Fetch & Input Gate)**

1. Оркестратор инициализируется по ID задачи (например, run-task PROJ-1024).  
2. Программа совершает HTTP-запрос к API таск-трекера и выкачивает полный контекст тикета.  
3. **Quality Gate №1:** Строгий контур проверяет параметры задачи.  
   * *Критерий проверки:* Поля описания и критериев приемки не должны быть пустыми. Длина текста должна превышать заданный лимит токенов для исключения тикетов вида «Сделай как надо».  
   * *Действие при сбое:* Пайплайн останавливается незамедлительно, не нагружая LLM. Пользователю выводится ошибка: \[CRITICAL\] Task description is insufficient. Missing Acceptance Criteria.

### **Этап 2: Проектирование решения (Plan & Design)**

1. Выгруженный контекст отправляется **Агенту-Архитектору**.  
2. Модель обязана проанализировать структуру существующего кода локального репозитория и выдать три строго структурированных артефакта в формате JSON и Markdown:  
   * design.json / design.md — затронутые файлы, новые интерфейсы, изменения в API-слое.  
   * implementation\_plan.json — пошаговый алгоритм модификации файлов (шаг 1, шаг 2, шаг 3).  
   * qa\_plan.json — тест-план (какие сценарии обязаны покрыть тесты, какие граничные значения проверить).  
3. **Интерактивное уточнение (Human-in-the-Loop):**  
   * Если Агенту-Архитектору не хватает данных или логика приложения содержит противоречия, оркестратор останавливает автоматический поток.  
   * В Telegram-канал (или локальное CLI/UI окно) отправляется структурированное оповещение с перечнем вопросов.  
   * После ввода ответов человеком, они сохраняются в user\_clarifications.json, и этап планирования перезапускается с учетом новых вводных.  
4. **Quality Gate №2 (Design Review):**  
   * Сгенерированные файлы планов верифицируются **Агентом-Критиком**.  
   * *Правило перехода:* Если обнаружены явные нарушения паттернов проектирования или риски безопасности, вызывается цикл исправления планов. Если блокирующие замечания отсутствуют, выставляется статус Design Approved, отправляется уведомление в Telegram/Slack, и пайплайн переходит на этап кодинга.

### **Этап 3: Кодирование (Implement)**

1. Оркестратор переключает контекст на **Агента-Программиста**.  
2. На вход модели подаются исключительно файлы design.json и implementation\_plan.json. **Исходный абстрактный тикет Jira на этот этап не допускается**, чтобы исключить вольные интерпретации требований моделью.  
3. Модель модифицирует кодовую базу в рамках изолированной локальной ветки Git (например, feature/PROJ-1024).

### **Этап 4: Статический анализ кода (Linter Gate)**

1. Программа запускает установленный в системе линтер проекта.  
2. **Quality Gate №3 & Feedback Loop:**  
   * *Условие проверки:* Если утилита нашла нарушения стандартов кодирования или синтаксические ошибки (Exit Code \!= 0):  
   * *Действие:* Оркестратор блокирует продвижение кода. Логи ошибок линтера упаковываются в промпт для **Агента-Программиста**. Программа выполняет сброс измененных файлов к исходной точке начала кодирования. Агент получает команду: *«Код нарушает правила линтера. Исправь следующие ошибки: \[Лог ошибок\]»*.  
   * Шаг зацикливается до тех пор, пока линтер не выдаст абсолютно чистый лог (Exit Code \== 0).

### **Этап 5: Динамическое тестирование логики (Test Gate)**

1. Оркестратор выполняет автоматический прогон модульных и интеграционных тестов через локальный командный интерпретатор. На этом же этапе Агент может сгенерировать новые модульные тесты, основываясь на ранее созданном артефакте qa\_plan.json.  
2. **Quality Gate №4 & Feedback Loop:**  
   * *Условие проверки:* Падение хотя бы одного тест-кейса.  
   * *Действие:* Полный текст стектрейса ошибки и логи падающих тестов передаются **Агентом-Программисту**. Происходит откат изменений. Агент приступает к багфиксингу.  
   * *Важное системное ограничение:* После внесения любых исправлений на этапе отладки тестов, код **обязан вернуться на Этап 4 (Linter)**, и только после повторного успешного прохождения линтера снова допускается на Этап 5 (Tests). Любое локальное исправление логики потенциально ломает синтаксис.

### **Этап 6: Семантическое код-ревью (Code Review Gate)**

1. Программа вызывает **Агента-Критика (Reviewer)**. Ему передаются исходный design.json, изначальный код и получившийся итоговый git diff.  
2. Задача Агента — проверить читаемость кода, отсутствие избыточной сложности (Overengineering) и соответствие архитектурной концепции, чего не могут определить автоматические тесты.  
3. **Quality Gate №5 & Фильтрация рисков:**  
   * Замечания гранулируются по уровням: Low, Medium, High, Critical, Blocker.  
   * Контур настраивается программно на порог жесткости. Например, если в конфигурации оркестратора выставлен порог High Critical, то мелкие замечания уровня Medium игнорируются (записываются в отчет review\_summary.md для информации), а процесс идет дальше. Если обнаружено замечание уровня High или Blocker — пайплайн блокируется и уходит в глобальный цикл исправления (Fix Loop \-\> Implement \-\> Linter \-\> Tests \-\> Re-Review).

### **Этап 7: Финализация и интеграция в репозиторий (Git Push & PR)**

1. После того как все Quality Gates вернули статус SUCCESS / APPROVED, задача официально переводится оркестратором в статус Task Complete.  
2. Автоматика выполняет коммит и отправку:  
   * git add . — индексация проверенных файлов.  
   * git commit \-m "feat(PROJ-1024): \[Автоматический коммит на основе ИИ-плана реализации\]" — генерация коммит-сообщения.  
   * git push origin feature/PROJ-1024 — отправка ветки в удаленный репозиторий.  
3. Через API оркестратор создает Pull Request в ветку main/master. В описание PR автоматически встраиваются ссылки на человекочитаемые артефакты из папки .agent\_weaver/ (design.md, review\_summary.md), подтверждающие успешное прохождение всех этапов контроля качества.

## **6\. Чек-лист для полной проверки программной логики агента**

Перед запуском вашего AI-агента в эксплуатацию убедитесь, что в коде оркестратора выполнены все защитные механизмы концепции Agent Harness:

* \[ \] **Изоляция шагов:** Агент-Программист физически не имеет доступа к исходному тексту тикета Jira, а видит только декомпозированный design.json.  
* \[ \] **Перехват Exit-кодов:** Валидация этапов завязана на системные коды возврата утилит ОС (Exit Code 0/1), а не на текстовый анализ ответа модели.  
* \[ \] **Автоматический Rollback:** Перед каждой итерацией исправления (Fix Loop) оркестратор выполняет сброс неоткомпилированного кода к стабильной сохраненной точке, предотвращая накопление «мусорного» кода от неудачных попыток ИИ.  
* \[ \] **Лимит итераций:** В стейт-машине жестко прописан верхний порог циклов самоисправления, исключающий зацикливание агента при неверных тестах или багах компилятора.  
* \[ \] **Интерактивные шлюзы:** При возникновении архитектурной неопределенности система умеет переходить в режим ожидания ответа человека (Human-in-the-loop), сохраняя текущую сессию пайплайна.  
* \[ \] **Постоянство артефактов:** Все промежуточные планы и отчеты ревью записываются на физический диск в структурированном виде, обеспечивая полную наблюдаемость (*Observability*) процесса для последующего аудита.
