Навіщо це взагалі

Чат-бот працює на демо. І розвалюється на проді.

Модель забуває, що робила три кроки тому. Виклики інструментів тихо падають. Контекстне вікно забивається непотребом. Проблема — не в моделі. Вона в усьому, що її оточує.

Доказ, що це саме каркас

LangChain змінили лише інфраструктуру навколо LLM — та сама модель, ті самі ваги — і піднялись з-поза топ-30 на 5-те місце у TerminalBench 2.0. Окремий проєкт дав LLM самій оптимізувати каркас → 76,4% і обійшов ручні системи.

Висновок

Два продукти на однаковій моделі дають радикально різний результат — лише через дизайн каркаса. На TerminalBench зміна каркаса рухає агента на >20 позицій.

Наступного разу, коли агент зазнає невдачі — не звинувачуй модель. Подивись на каркас.

Що таке каркас · анатомія

Три рівні інженерії, дванадцять компонентів

Промпт-інженерія формує інструкції. Контекстна керує тим, що і коли бачить модель. Інженерія каркаса охоплює обидві + усю інфраструктуру: оркестрацію, стан, відновлення, перевірку, безпеку.

Ядро

  • Цикл оркестрації — «тупий цикл», увесь інтелект у моделі
  • Розбір результату — нативний tool_calls, не текст-парсинг
  • Побудова промпту — Codex: system→tools→dev→user AGENTS.md (32 KiB)→history

Здібності

  • Інструменти — схема+ізольоване виконання, 6 категорій у Claude Code
  • Пам'ять — 3 рівні: індекс ~150 симв. → тематичні файли → сирі транскрипти (пошук); пам'ять = «підказка», не факт
  • Контекст — деградація >30% в середині вікна (Lost in the Middle)

Надійність

  • Керування станом — LangGraph: типізовані словники+чекпоінти; Claude Code: git-коміти
  • Помилки — 10 кроків × 99% = лише ~90,4% наскрізь; Stripe: ліміт 2 повтори
  • Цикли перевірки — правила / візуальна / LLM-суддя, ×2–3 якість (Cherny)

Масштаб

  • Guardrails — OpenAI 3 шари (вхід/вихід/інструмент); Anthropic: дозволи окремо від мислення моделі
  • Субагенти — Claude Code: Fork/Teammate/Worktree
  • Життєвий цикл — керування від старту до фінішу, тримає решту 11 компонентів разом
Каркас багатошаровий — не одна обгортка навколо промпту.
Цикл · серцебиття каркаса

Механічно — це просто цикл while

Думка → Дія → Спостереження (ReAct): зібрати промпт → інференс → класифікувати результат → виконати інструменти → запакувати → оновити контекст → повторити.

Anthropic називає своє середовище «тупим циклом»: увесь інтелект — у моделі, каркас лише керує ходами. Складність — не в циклі, а в кожному його кроці.

  • Умови виходу: відповідь без інструментів · ліміт ходів · бюджет токенів · захисне обмеження · перерив користувача
  • Процес із 10 кроків по 99% успіху = лише ~90% наскрізь. Помилки накопичуються — тому перевірка на кожному кроці критична.
Простий механічно — складний у кожному кроці.
② Loop Engineering

Коли задача не влазить в одне контекстне вікно

Один цикл упирається в межі вікна. Loop Engineering — це повторення циклу з пам'яттю у файлах, крізь багато вікон. Anthropic формалізували це як «Ralph Loop»:

Фаза 1 — ініціалізатор

Готує середовище: сценарій, файл прогресу, перелік функцій, початковий git-коміт.

Фаза 2 — кодувальник (щоразу з чистим вікном)

Читає git-логи + файл прогресу → орієнтується → бере найпріоритетнішу незавершену функцію → працює → коміт → пише підсумок. Файлова система = безперервність між вікнами.

«Я більше не промпчу Claude вручну. У мене є петлі, які промптять Claude і самі вирішують, що робити далі. Моя робота — писати петлі.»

Boris Cherny · Head of Claude Code, Anthropic
Сім рішень, що визначають кожен каркас

Головна ставка — товщина каркаса

Метафора риштувань: коли будівля готова — риштування прибирають. Manus перебудовано 5 разів за 6 місяців, кожного разу прибираючи складність каркаса на користь моделі.

  • 1. Один агент чи кілька — спочатку максимум з одного; ділити лише при >10 інструментів із перетином або чітко окремих доменах
  • 2. ReAct чи Plan-Execute — ReAct гнучкий, дорожчий на кроці; LLMCompiler (plan-execute) — ×3,6 швидше
  • 3. Стратегія контексту — очищення / підсумовування / маскування / нотатки / субагенти; ACON: –26–54% токенів, точність >95%
  • 4. Дизайн перевірки — «напрямні» (guides, до дії) vs «сенсори» (sensors, після) — термінологія Thoughtworks/Fowler
  • 5. Дозволи — дозвільний (швидко, ризиковано) vs обмежувальний (безпечно, повільно)
  • 6. Набір інструментів — менше = краще: Vercel прибрала 80% із v0; Claude Code — 95% економії контексту lazy-load
  • 7. Товщина каркаса — Тонкий: довіряй моделі. Товстий: логіка в коді. Anthropic регулярно видаляє кроки з Claude Code, коли модель засвоює їх сама.

Тест на майбутнє: якщо продуктивність росте з силою моделі без додавання складності каркаса — дизайн вдалий.

③ Від теорії — до нашого коду

У нас це не теорія. Це працюючий каркас.

Все вище — це креслення. Тепер — наша реалізація. Два інструменти, дві ролі:

🚪 elt-code — двері

Тонкий роутер (71 рядок). Розпізнає намір із повідомлення і направляє роботу в потрібний рушій. Нічого не «думає» сам — це найтонший можливий шар.

↻ elt-loop — петля

Це і є Ralph Loop у нас. Бере наступну задачу зі tasks.md, імплементить, закриває механічним оракулом, комітить, оновлює пам'ять — і сам переходить до наступного слайса.

Далі — схема, як саме воно збудоване, з прив'язкою кожного боксу до компонента каркаса з теорії.

Головна ставка каркаса · перевірка

Оракул закриває петлю. Суддя — лише розповідає.

🧪 Обчислювальна перевірка = істина

just test реально запускає код. exit 0 = зелено, і крапка. Детерміновано. Це — жорсткий гейт: слайс закритий ⇔ оракул зелений.

⚖️ Висновкова (LLM-суддя) = семантика

Ловить scope-creep, ослаблені тести. Але суддя виконався 0 із 46 разів — це був театр. Тому в нас суддя не закриває петлю. Закривають ТЕСТИ.

«Дати моделі спосіб перевірити власну роботу покращує якість у 2–3 рази.»

Boris Cherny · творець Claude Code

Термінологія Thoughtworks (M. Fowler): «напрямні» (guides) — вплив до дії; «сенсори» (sensors) — зворотний зв'язок після. Наш гейт — це сенсор із зубами.

5 запитань будь-якому «автономному AI»

  • Хто закриває задачу — механічна перевірка чи AI на слово?
  • Хто перевіряє — окремий агент чи виконавець сам собі суддя?
  • Є кнопка «стоп» (kill-switch)?
  • Є ліміт спроб (щоб не зациклився)?
  • Пам'ять живе у файлі — чи зникає з новою розмовою?

У нас на всі 5 — «так»

оракул закриває · суддя-субагент перевіряє · loop: PAUSED · self-heal ≤3 · STATE.md у проєкті.

  • Чесна прогалина: нема ізоляції слайса в окремому worktree — але це про паралельні конфлікти, не про «поганий код» (від нього вже захищає оракул+гейт).
  • Ставка на тонкий каркас: довіряємо моделі, зубів рівно стільки, щоб не пустити недороблене.
