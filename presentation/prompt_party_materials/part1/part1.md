Ви створили чатбота. Можливо, під’єднали цикл ReAct із кількома інструментами. Для демонстрацій це працює. Але щойно ви намагаєтеся створити рішення виробничого рівня, усе починає розвалюватися: модель забуває, що робила три кроки тому, виклики інструментів тихо завершуються помилкою, а контекстні вікна заповнюються непотребом.

Проблема не у вашій моделі. Проблема — в усьому, що її оточує.

LangChain довела це, змінивши лише інфраструктуру навколо своєї LLM — за тієї самої моделі й тих самих ваг — і піднявшись із позиції поза першою тридцяткою на 5-те місце в TerminalBench 2.0. Окремий дослідницький проєкт досяг показника проходження 76,4%, доручивши LLM оптимізувати саму інфраструктуру, і перевершив системи, спроєктовані вручну.

Тепер ця інфраструктура має назву: каркас агента.

Що таке каркас агента?
Термін було формалізовано на початку 2026 року, але сама концепція існувала значно раніше. Каркас — це повна програмна інфраструктура навколо LLM: цикл оркестрації, інструменти, пам’ять, керування контекстом, збереження стану, опрацювання помилок і захисні обмеження. У документації Anthropic щодо Claude Code це сформульовано просто: SDK — це «каркас агента, на якому працює Claude Code». Команда OpenAI Codex використовує таке саме трактування, прямо прирівнюючи терміни «агент» і «каркас» для позначення немодельної інфраструктури, яка робить LLM корисною.

Мені дуже подобається канонічна формула Вівека Тріведі з LangChain: «Якщо ви не модель, то ви — каркас».

Ось відмінність, яка часто збиває людей з пантелику. «Агент» — це поведінка, що виникає в системі: орієнтована на мету сутність, яка використовує інструменти, виправляє себе й взаємодіє з користувачем. Каркас — це механізм, який породжує таку поведінку. Коли хтось каже: «Я створив агента», це означає, що він створив каркас і під’єднав до нього модель.



Беррен Міллідж точно сформулював цю аналогію у своєму есе 2023 року «Scaffolded LLMs as Natural Language Computers». Сира LLM — це процесор без оперативної пам’яті, диска та вводу-виводу. Контекстне вікно виконує роль оперативної пам’яті — швидкої, але обмеженої. Зовнішні бази даних працюють як дискове сховище — велике, але повільне. Інтеграції з інструментами діють як драйвери пристроїв. Каркас є операційною системою. Як писав Міллідж: «Ми заново винайшли архітектуру фон Неймана», оскільки вона є природною абстракцією для будь-якої обчислювальної системи.

Три рівні інженерії
Навколо моделі існують три концентричні рівні інженерії:

·        Промпт-інженерія формує інструкції, які отримує модель.

·        Контекстна інженерія керує тим, що і коли бачить модель.

·        Інженерія каркаса охоплює обидва попередні рівні, а також усю інфраструктуру застосунку: оркестрацію інструментів, збереження стану, відновлення після помилок, цикли перевірки, забезпечення безпеки та керування життєвим циклом.

Каркас — це не обгортка навколо промпту. Це повна система, яка робить можливою автономну поведінку агента.

12 компонентів виробничого каркаса
Якщо узагальнити підходи Anthropic, OpenAI, LangChain і ширшої спільноти практиків, виробничий каркас агента містить дванадцять окремих компонентів. Розгляньмо кожен із них.



1. Цикл оркестрації
Це серцебиття системи. Він реалізує цикл «Думка — Дія — Спостереження» (Thought-Action-Observation, TAO), який також називають циклом ReAct. Послідовність така: зібрати промпт, викликати LLM, розібрати результат, виконати виклики інструментів, повернути результати моделі й повторювати до завершення.

Механічно це часто лише цикл while. Складність міститься в усьому, чим цей цикл керує, а не в самому циклі. Anthropic описує своє середовище виконання як «тупий цикл», у якому весь інтелект міститься в моделі. Каркас лише керує ходами.

2. Інструменти
Інструменти — це руки агента. Вони визначаються як схеми — назва, опис і типи параметрів — та додаються до контексту LLM, щоб модель знала, що їй доступно. Рівень інструментів відповідає за реєстрацію, перевірку схем, вилучення аргументів, виконання в ізольованому середовищі, збирання результатів і форматування результатів як зрозумілих для LLM спостережень.

Claude Code надає інструменти шести категорій: операції з файлами, пошук, виконання, доступ до вебу, інтелектуальний аналіз коду та запуск субагентів. OpenAI Agents SDK підтримує функціональні інструменти через @function_tool, розміщені інструменти WebSearch, CodeInterpreter і FileSearch, а також інструменти серверів MCP.

3. Пам’ять
Пам’ять працює на кількох часових масштабах. Короткострокова пам’ять — це історія розмови в межах одного сеансу. Довгострокова пам’ять зберігається між сеансами: Anthropic використовує файли проєкту CLAUDE.md та автоматично створені файли MEMORY.md; LangGraph використовує організовані за просторами імен JSON-сховища; OpenAI підтримує Sessions на базі SQLite або Redis.

Claude Code реалізує трирівневу ієрархію: легкий індекс приблизно по 150 символів на запис, який завжди завантажено; детальні тематичні файли, що підтягуються за потреби; та сирі стенограми, доступні лише через пошук. Критичний принцип проєктування полягає в тому, що агент сприймає власну пам’ять як «підказку» і перед дією перевіряє її за фактичним станом.

4. Керування контекстом
Саме тут багато агентів непомітно зазнають невдачі. Основна проблема — деградація контексту: продуктивність моделі знижується більш ніж на 30%, коли ключовий вміст опиняється в середині контекстного вікна. Це показали дослідження Chroma, що узгоджуються з висновками Стенфорда «Lost in the Middle». Навіть контекстні вікна на мільйон токенів демонструють погіршення дотримання інструкцій зі зростанням контексту.

Виробничі стратегії включають:

·        Стиснення: підсумовування історії розмови під час наближення до ліміту. Claude Code зберігає архітектурні рішення та невирішені помилки, відкидаючи дубльовані результати інструментів.

·        Маскування спостережень: Junie від JetBrains приховує старі результати інструментів, залишаючи видимими самі виклики.

·        Отримання точно в потрібний момент: зберігання легких ідентифікаторів і динамічне завантаження даних. Claude Code використовує grep, glob, head і tail замість завантаження повних файлів.

·        Делегування субагентам: кожен субагент може широко досліджувати питання, але повертає лише стислий підсумок на 1 000–2 000 токенів.

У посібнику Anthropic із контекстної інженерії мета сформульована так: знайти найменший можливий набір високосигнальних токенів, який максимально підвищує ймовірність бажаного результату.

5. Побудова промпту
Цей компонент збирає те, що модель фактично бачить на кожному кроці. Структура є ієрархічною: системний промпт, визначення інструментів, файли пам’яті, історія розмови та поточне повідомлення користувача.

OpenAI Codex використовує суворий стек пріоритетів: системне повідомлення, кероване сервером, має найвищий пріоритет; далі йдуть визначення інструментів, інструкції розробника, інструкції користувача — каскадні файли AGENTS.md з лімітом 32 КіБ — і лише потім історія розмови.

6. Розбір результату
Сучасні каркаси покладаються на нативний виклик інструментів, коли модель повертає структуровані об’єкти tool_calls, а не вільний текст, який потрібно розбирати. Каркас перевіряє: є виклики інструментів — виконує їх і продовжує цикл; немає викликів — це фінальна відповідь.

Для структурованих результатів OpenAI і LangChain підтримують відповіді, обмежені схемою, через моделі Pydantic. Застарілі підходи на кшталт RetryWithErrorOutputParser — який повертає моделі початковий промпт, невдале завершення та помилку розбору — залишаються доступними для крайових випадків.

7. Керування станом
LangGraph моделює стан як типізовані словники, що проходять через вузли графа, а редуктори об’єднують оновлення. Контрольні точки створюються на межах суперкроків, що дає змогу відновлювати роботу після переривань і виконувати налагодження з «подорожжю в часі». OpenAI пропонує чотири взаємовиключні стратегії: пам’ять застосунку, сесії SDK, серверний Conversations API або легке зв’язування через previous_response_id. Claude Code використовує інший підхід: коміти Git як контрольні точки та файли прогресу як структуровані чернетки.

8. Опрацювання помилок
Ось чому це важливо: процес із 10 кроків, кожен із яких має 99% успішності, забезпечує лише приблизно 90,4% наскрізної успішності. Помилки швидко накопичуються.

LangGraph розрізняє чотири типи помилок: тимчасові — повторити зі збільшенням затримки; виправні LLM — повернути помилку як ToolMessage, щоб модель могла скоригувати дії; виправні користувачем — перервати роботу та запросити введення людини; неочікувані — передати нагору для налагодження. Anthropic перехоплює збої всередині обробників інструментів і повертає їх як результати з помилкою, щоб цикл продовжувався. Виробничий каркас Stripe обмежує кількість повторних спроб двома.

9. Захисні обмеження та безпека
SDK OpenAI реалізує три рівні: вхідні захисні обмеження, що виконуються на першому агенті; вихідні, що перевіряють фінальний результат; та обмеження інструментів, які застосовуються до кожного виклику. Механізм «аварійного дроту» негайно зупиняє агента після спрацювання.

Anthropic архітектурно відокремлює контроль дозволів від міркувань моделі. Модель вирішує, що спробувати зробити; система інструментів вирішує, що дозволено. Claude Code окремо контролює близько 40 можливостей інструментів у три етапи: встановлення довіри під час завантаження проєкту, перевірка дозволу перед кожним викликом інструмента та явне підтвердження користувача для операцій із високим ризиком.

10. Цикли перевірки
Саме це відрізняє демонстраційні іграшки від виробничих агентів. Anthropic рекомендує три підходи: зворотний зв’язок на основі правил — тести, лінтери й перевірки типів; візуальний зворотний зв’язок — знімки екрана через Playwright для завдань інтерфейсу; та LLM як суддя — окремий субагент оцінює результат.

Борис Черні, творець Claude Code, зазначив, що надання моделі способу перевірити власну роботу покращує якість у 2–3 рази.

11. Оркестрація субагентів
Claude Code підтримує три моделі виконання: Fork — побайтова копія контексту батьківського агента; Teammate — окрема панель термінала з обміном повідомленнями через файли; Worktree — власне робоче дерево Git та ізольована гілка для кожного агента. SDK OpenAI підтримує агентів як інструменти, коли спеціаліст виконує обмежене підзавдання, та передавання керування, коли спеціаліст повністю перебирає контроль. LangGraph реалізує субагентів як вкладені графи стану.
