Цикл у русі: покроковий розбір
Тепер, коли компоненти відомі, простежмо, як вони працюють разом у межах одного циклу.



Крок 1 — збирання промпту
Каркас формує повний вхід: системний промпт + схеми інструментів + файли пам’яті + історія розмови + поточне повідомлення користувача. Важливий контекст розміщується на початку та в кінці промпту відповідно до висновку «Lost in the Middle».

Крок 2 — інференс LLM
Зібраний промпт передається API моделі. Модель генерує текст, запити на виклик інструментів або обидва типи результату.

Крок 3 — класифікація результату
Якщо модель створила текст без викликів інструментів, цикл завершується. Якщо запитано інструменти, система переходить до виконання. Якщо запитано передавання керування, поточний агент змінюється і цикл починається знову.

Крок 4 — виконання інструментів
Для кожного виклику каркас перевіряє аргументи, контролює дозволи, виконує дію в ізольованому середовищі та збирає результати. Операції лише для читання можуть виконуватися паралельно; операції зі зміною стану — послідовно.

Крок 5 — пакування результатів
Результати інструментів форматуються як повідомлення, зрозумілі для LLM. Помилки перехоплюються і повертаються як результати з помилкою, щоб модель могла самостійно виправитися.

Крок 6 — оновлення контексту
Результати додаються до історії розмови. Якщо система наближається до межі контекстного вікна, каркас запускає стиснення.

Крок 7 — повторення циклу
Повернення до кроку 1. Цикл повторюється до завершення.

Умови завершення є багаторівневими: модель створює відповідь без викликів інструментів; перевищено максимальну кількість ходів; вичерпано бюджет токенів; спрацювало захисне обмеження; користувач перервав роботу; або повернуто відмову з міркувань безпеки. Просте запитання може потребувати 1–2 ходів. Складне завдання з рефакторингу може поєднати десятки викликів інструментів у багатьох ходах.

Для довготривалих завдань, що охоплюють кілька контекстних вікон, Anthropic розробила двофазний шаблон «Ralph Loop»: агент-ініціалізатор готує середовище — сценарій ініціалізації, файл прогресу, перелік функцій і початковий коміт Git; потім агент-кодувальник у кожному наступному сеансі читає журнали Git і файли прогресу, щоб зорієнтуватися, обирає найпріоритетнішу незавершену функцію, працює над нею, створює коміт і записує підсумки. Файлова система забезпечує безперервність між контекстними вікнами.

Як реальні фреймворки реалізують цей шаблон


Claude Agent SDK від Anthropic відкриває каркас через одну функцію query(), яка створює агентний цикл і повертає асинхронний ітератор із потоковими повідомленнями. Середовище виконання — це «тупий цикл»: весь інтелект міститься в моделі. Claude Code використовує цикл «Зібрати — Діяти — Перевірити»: зібрати контекст через пошук файлів і читання коду, виконати дію через редагування файлів і запуск команд, перевірити результат через тести й аналіз виводу, після чого повторити.

OpenAI Agents SDK реалізує каркас через клас Runner у трьох режимах: асинхронному, синхронному та потоковому. SDK є «орієнтованим на код»: логіка робочого процесу виражається у звичайному Python, а не в предметно-специфічних мовах графів. Каркас Codex розширює це трирівневою архітектурою: Codex Core — код агента та середовище виконання; App Server — двонапрямний API JSON-RPC; клієнтські поверхні — CLI, VS Code і вебзастосунок. Усі поверхні використовують той самий каркас, тому «моделі Codex краще відчуваються в інтерфейсах Codex, ніж у звичайному вікні чату».

LangGraph моделює каркас як явний граф стану. Два вузли — llm_call і tool_node — з’єднані умовним ребром: якщо є виклики інструментів, маршрут веде до tool_node; якщо їх немає — до END. LangGraph розвинувся з AgentExecutor у LangChain, який було оголошено застарілим у версії 0.2 через складність розширення та відсутність підтримки мультиагентних систем. Deep Agents у LangChain прямо використовують термін «каркас агента»: вбудовані інструменти, планування через write_todos, файлові системи для керування контекстом, запуск субагентів і постійна пам’ять.

CrewAI реалізує рольову мультиагентну архітектуру: Agent — каркас навколо LLM, визначений роллю, метою, передісторією та інструментами; Task — одиниця роботи; Crew — набір агентів. Рівень Flows у CrewAI додає «детермінований хребет з інтелектом там, де він потрібен», керуючи маршрутизацією та перевіркою, тоді як Crews забезпечують автономну співпрацю.

AutoGen, що розвивається в Microsoft Agent Framework, започаткував оркестрацію через розмову. Його трирівнева архітектура — Core, AgentChat і Extensions — підтримує п’ять шаблонів: послідовний, паралельний із розгалуженням і збиранням, груповий чат, передавання керування та magentic, у якому агент-менеджер веде динамічний журнал завдань і координує спеціалістів.

Метафора будівельних риштувань
Метафора риштувань не є декоративною — вона точна. Будівельні риштування є тимчасовою інфраструктурою, яка дає працівникам змогу зводити конструкцію, до якої вони інакше не дісталися б. Риштування не виконують будівельні роботи. Але без них працівники не зможуть досягти верхніх поверхів.



Ключова ідея полягає в тому, що після завершення будівлі риштування прибирають. З удосконаленням моделей складність каркаса має зменшуватися. Manus було перебудовано п’ять разів за шість місяців, і кожне перепроєктування прибирало складність. Складні визначення інструментів перетворилися на загальне виконання команд оболонки. «Керувальні агенти» стали простими структурованими передаваннями керування.

Це вказує на принцип спільної еволюції: моделі тепер донавчаються з конкретними каркасами в циклі. Модель Claude Code навчилася використовувати конкретний каркас, із яким її тренували. Зміна реалізації інструментів може погіршити продуктивність через цей тісний зв’язок.

«Тест на готовність до майбутнього» для дизайну каркаса: якщо продуктивність зростає разом із потужністю моделей без додавання складності каркаса, дизайн є вдалим.



Сім рішень, що визначають кожен каркас
Кожен архітектор каркаса має зробити сім виборів:



1. Один агент чи кілька агентів. Anthropic і OpenAI радять спочатку максимально використати одного агента. Мультиагентні системи додають накладні витрати — додаткові виклики LLM для маршрутизації та втрату контексту під час передавання керування. Розділяти систему варто лише тоді, коли перевантаження інструментами перевищує приблизно 10 інструментів із перетинними функціями або існують чітко відокремлені предметні області.

2. ReAct чи «планування та виконання». ReAct чергує міркування і дію на кожному кроці — це гнучко, але дорожче на кожному етапі. Підхід «планування та виконання» відокремлює планування від виконання. LLMCompiler повідомляє про прискорення у 3,6 раза порівняно з послідовним ReAct.

3. Стратегія керування контекстним вікном. П’ять виробничих підходів: очищення за часом, підсумовування розмови, маскування спостережень, структуроване ведення нотаток і делегування субагентам. Дослідження ACON показало скорочення токенів на 26–54% зі збереженням точності понад 95% завдяки пріоритизації слідів міркувань над сирими результатами інструментів.

4. Дизайн циклу перевірки. Обчислювальна перевірка — тести та лінтери — дає детерміновану істину. Висновкова перевірка через LLM-суддю виявляє семантичні проблеми, але додає затримку. Команда Thoughtworks Мартіна Фаулера описує це як «напрямні» — попереджувальний вплив до дії — та «сенсори» — зворотний зв’язок після дії.

5. Архітектура дозволів і безпеки. Дозвільний підхід є швидким, але ризикованим і автоматично схвалює більшість дій. Обмежувальний підхід безпечніший, але повільніший, оскільки потребує схвалення кожної дії. Вибір залежить від середовища розгортання.

6. Стратегія визначення набору інструментів. Більша кількість інструментів часто означає гіршу продуктивність. Vercel прибрала 80% інструментів із версії v0 і отримала кращі результати. Claude Code досягає 95% скорочення контексту завдяки лінивому завантаженню. Принцип: показувати мінімальний набір інструментів, потрібний для поточного кроку.

7. Товщина каркаса. Йдеться про те, скільки логіки міститься в каркасі, а скільки — у моделі. Anthropic робить ставку на тонкі каркаси та вдосконалення моделей. Графові фреймворки роблять ставку на явний контроль. Anthropic регулярно видаляє етапи планування з каркаса Claude Code, коли нові версії моделі внутрішньо засвоюють цю здатність.

Каркас і є продуктом
Два продукти, що використовують однакові моделі, можуть демонструвати радикально різну продуктивність лише через дизайн каркаса. Дані TerminalBench однозначні: зміна лише каркаса перемістила агентів більш ніж на 20 позицій у рейтингу.

Каркас не є розв’язаною проблемою або стандартним товарним шаром. Саме тут міститься складна інженерія: керування контекстом як дефіцитним ресурсом, проєктування циклів перевірки, які виявляють збої до їх накопичення, створення систем пам’яті, що забезпечують безперервність без галюцинацій, та архітектурні рішення щодо того, скільки риштувань будувати, а скільки залишати моделі.

Галузь рухається до тонших каркасів у міру вдосконалення моделей. Але сам каркас не зникне. Навіть найпотужнішій моделі потрібне щось, що керує її контекстним вікном, виконує виклики інструментів, зберігає стан і перевіряє роботу.

Наступного разу, коли ваш агент зазнає невдачі, не звинувачуйте модель. Подивіться на каркас.
