## Что это такое (020 T010)

Эта команда — **UI над рантаймом**, а не сам рецепт. Рецепт живёт в коде:
`tools/review-runtime.js` (`runReview`), и его же вызывает `runJudge` — то есть и синхронный
гейт, и фоновая проверка. До T010 рецепт существовал ТОЛЬКО как текст здесь, и выполнялся
ровно настолько, насколько его в этот раз прочитал агент; из `tools/` и `bin/` линзы не
запускались ни разу.

Что рантайм гарантирует механически, а не просьбой:

- пять `agents/review-*.md` идут **параллельно** на одном диффе (`Promise.all`), неполный
  набор линз — отказ, а не «ревью, сколько нашлось»;
- потом **ровно один** `confidence-scorer` даёт финальную классификацию по рубрике 0–100;
- `>= 80` блокирует, `< 80` уходит в `.elt/ledger.jsonl` как `weak-signal` — сам, без
  напоминания;
- мёртвая линза или мёртвый оценщик — **отдельное состояние `review-dead`**, никогда не
  зелёное: вердикт четырёх линз не выдаётся за вердикт пяти.

Контракт закреплён в `tools/review-runtime.test.js` (параллельность, ровно один вызов
оценщика, отказ на мёртвой линзе, перекрытие самооценки линзы оценщиком).

## Задача

Аргументы: `$ARGUMENTS` (пусто — ревьюим незакоммиченные изменения; иначе — названную
ревизию или диапазон).

### Путь 1 (предпочтительный): рантайм проекта

Если в `.harness/harness.json` включено `review: { "enabled": true }`, ревью уже выполняется
внутри гейта — отдельно запускать его не нужно. Посмотреть результат:

```bash
node tools/elt.js review --json      # очередь разбора, включая слабые сигналы
node bin/ledger.js summary           # накопление weak-signal по правилам
```

Включить в проекте (решение проектное — пять модельных вызовов на каждый вызов судьи):

```bash
node -e "const f='.harness/harness.json',c=require('fs');const j=JSON.parse(c.readFileSync(f,'utf8'));j.review={enabled:true};c.writeFileSync(f,JSON.stringify(j,null,2)+'\n')"
```

### Путь 2: ручной прогон здесь и сейчас

Когда рантайм в проекте выключен, а посмотреть надо — воспроизведи ТОТ ЖЕ порядок субагентами.
Он обязан совпадать с рантаймом, иначе ручное ревью и гейт будут расходиться в вердиктах.

1. **Дифф.** `git diff` (или названная ревизия) — один и тот же дифф на все пять линз.
2. **Пять линз — ОДНИМ сообщением, параллельно** (не по очереди): `review-bugs`,
   `review-claude-md`, `review-code-comments`, `review-history`, `review-prior-comments`.
   Каждая возвращает JSON-массив находок
   `{file, line, summary, failure_scenario, confidence}`. Линзы не видят ответов друг друга.
3. **Ровно одна отсечка.** Все находки одним списком — в `confidence-scorer`
   (`claude-haiku-4-5-20251001`). Оценка оценщика **перекрывает** самооценку линзы: линза
   заинтересована в своей находке.
4. **Классификация.** `>= 80` — блокирующее, называй файл, строку и сценарий отказа.
   `< 80` — слабый сигнал: не блокирует, но записывается:
   `node bin/ledger.js record --kind weak-signal --rule review/<линза> --note "<file>:<line> <summary>"`.
5. **Мёртвая линза — не «ноль находок».** Если линза не ответила или ответ нечитаем, скажи
   это прямо и НЕ объявляй ревью зелёным.

## Формат ответа

Сначала одна строка вердикта: `review-pass` / `review-block` / `review-inconclusive` /
`review-dead`. Затем блокирующие находки (файл, строка, сценарий отказа, оценка), затем
слабые сигналы одним списком. Ничего не «улучшай» по дороге: ревью не правит код.
