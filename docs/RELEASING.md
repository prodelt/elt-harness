# Релиз ELT

Протокол один и не сокращается. Он длиннее, чем «поставить тег», по одной причине:
**сертификат обязан относиться к дереву, которое после него не менялось**. Любая запись в
дерево после сертификата делает его ложью, поэтому порядок шагов — часть гарантии, а не
формальность.

## SemVer

| шаг | когда |
| --- | --- |
| `major` | сломан контракт: убрана команда, изменена схема журнала/сертификата, снята эпоха |
| `minor` | новая способность, старые маршруты работают как прежде |
| `patch` | исправление без изменения контракта |

Версия объявлена в четырёх местах: `.claude-plugin/plugin.json`,
`.claude-plugin/marketplace.json` (дважды — `metadata` и запись плагина) и `CHANGELOG.md`.
Ни одно не является источником для остальных, поэтому согласованность проверяется механически:

```powershell
node tools/version-check.js            # файлы согласованы между собой
node tools/version-check.js --tag v5.0.0   # и тег указывает на ту же версию
```

Следующую версию не назначают на глаз:
`node -e "console.log(require('./tools/version-check').nextVersion('5.0.0','minor').version)"`.

## Протокол релиза

Порядок обязателен. Шаг 2 и далее выполняются **без единой записи** в дерево, к которому
привязан сертификат.

1. **`prepare-release` commit.** Всё, что меняется перед релизом, входит сюда и только сюда:
   версия в четырёх местах, `CHANGELOG.md`, `README.md`, `.planning/STATE.md`,
   `.planning/PROJECT-HISTORY.md`, разбор очереди. После этого коммита дерево заморожено.
2. **Полный оракул.** `node tools/elt.js oracle --full` — exit 0.
3. **Все пять линз и оценщик.** Независимо от impact-выборки: релиз — это high-risk по
   определению (`certification.requiredLenses('release')` возвращает все пять).
4. **Release certificate.** Вне дерева, в `.git/elt/certificates/`. Содержит `releaseId`,
   упорядоченные `specIdentities[]`, упорядоченные digest'ы включённых batch-сертификатов,
   commit/tree/graph/lock хеши и машинное доказательство, что открытых задач релиза нет.
   Batch-сертификат сам по себе права на релиз **не даёт** — это разные схемы.
5. **Annotated tag** на тот же коммит: `git tag -a v5.0.0 -m "..."`.
6. **Push и receipts.** `git push origin <branch> --follow-tags`, затем GitHub Release.
7. **Post-push verifier.** Перечитать remote-тег и сверить SHA:
   `git ls-remote --tags origin v5.0.0` — он обязан указывать на тот же коммит.

Любое изменение после шага 4 начинает протокол заново с шага 1. Не «подправить и
перевыпустить тег» — начать заново.

## Предрелизные гейты

Всё проверяется командой, а не глазами:

```powershell
node tools/elt.js oracle --full          # exit 0
node bin/doctor.js                        # FAIL=0
node tools/version-check.js               # версии согласованы
node tools/elt.js review --json           # очередь релиза пуста
node tools/elt.js batch --json            # нет батчей в карантине
node tools/graph-conformance.test.js      # маршрут соответствует графу
```

Плюс: remote CI зелёный на обеих платформах, ноль `bg-silent` и осиротевших worktree для
коммитов релиза.

**Наблюдательные пороги релиз не блокируют.** Adoption ≥80% за неделю и сигнал/шум ≥1:1 на
20 новых диффах — post-release промоушен-гейты; до полного окна они имеют статус
`not yet measured`. Показать их как pass раньше времени — то же враньё, что и красный тест,
объявленный зелёным.

## Защита тега и ветки

Включить branch protection и запрет force-push/удаления тега, если тариф и API позволяют.
Если не позволяют — записать **дословный текст отказа API** и `tagProtection: unavailable`
в receipts. В этом случае релиз не имеет права заявлять неизменяемость на стороне remote:
локальная привязка сертификата к хешам остаётся проверяемой, а remote-гарантии — нет.

## Что делать, если гейт красный

Ничего не сокращать. Красный гейт перед релизом — это RC, а не релиз: записать точный
блокер, последний зелёный SHA, открытые identity задач и одну команду возобновления.
Фальшивый тег дороже отложенного.
