## D13 — zone-чек в batch-коммите видит зону ТОЛЬКО первой задачи

**Статус:** новый. Не покрывается D9: там штрафовались файлы, которых задача не объявляла
(`package-lock.json`). Здесь файлы объявлены явно и дословно — просто вторая зона не читается.

**Наблюдение.** Зоны в `specs/003-admin-backfill-and-roles/tasks.md`:

```
T001 … [files:supabase/migrations/063_admin_backfill_work_day.sql,src/__tests__/lib/migration-063-admin-backfill.test.ts]
T002 … [files:supabase/migrations/064_profile_owner.sql,src/__tests__/lib/migration-064-profile-owner.test.ts]
```

Коммит `34a9168` тронул ровно эти 4 файла плюс `tasks.md` (галочки ставит сам харнесс).
Судья объявил out-of-scope **ровно два файла T002** и ни одного файла T001 — то есть
проверка отработала по первой зоне и не увидела вторую.

**Почему ломается.** Текст в гейт приходит склеенным по обеим задачам —
`C:\Users\espad\.claude\bin\elt.js:825` и `:1177`:

```js
cwd, tid: taskId, taskText: texts.join('\n'), specFile: binding.specPath,
```

А парсер зоны берёт только ПЕРВОЕ вхождение — `C:\Users\espad\.claude\bin\elt-gate-l0.js:171`:

```js
function taskScopeFiles(taskText) {
  const m = String(taskText || '').match(/\[files:([^\]]+)\]/);
  return m ? m[1].split(',').map((s) => s.trim()).filter(Boolean) : [];
}
```

`String.prototype.match()` с регуляркой БЕЗ флага `g` возвращает первое совпадение, а не все.
Зона T002 отбрасывается молча. Далее `elt-gate-l0.js:241-250` честно считает файлы T002
чужими.

**Механическая проверка.** Одна строка в node, без запуска харнесса:

```js
const t = "T001 [files:a.sql,a.test.ts] …\nT002 [files:b.sql,b.test.ts] …";
t.match(/\[files:([^\]]+)\]/)[1];        // → "a.sql,a.test.ts"   ← зона T002 потеряна
[...t.matchAll(/\[files:([^\]]+)\]/g)].map(m => m[1]);  // → обе зоны
```

**Следствие.** Любой batch-коммит на N > 1 задач гарантированно получает `out-of-scope` на
файлах задач 2..N. То есть режим, который CLI сам рекламирует в `--help` («БАТЧ: `--task
T001,T002,T003` — один оракул + один судья + один коммит на N задач»), несовместим со своим
же zone-чеком.

**Предлагается.** Объединять зоны всех задач батча:

```js
function taskScopeFiles(taskText) {
  return [...String(taskText || '').matchAll(/\[files:([^\]]+)\]/g)]
    .flatMap((m) => m[1].split(',').map((s) => s.trim()))
    .filter(Boolean);
}
```

Правка ровно в одной функции, поведение для одиночного слайса не меняется.

## D17 — judge-bench не может запустить судью: `propose` отклоняет ВСЁ

```json
{ "ok": false, "verdict": "rejected",
  "baseline": { "recall": 0.909, "falsePositiveRate": 0.4545 },
  "result":   { "recall": 0,     "falsePositiveRate": 0 } }
```

Все 58 кейсов легли одинаково:

```
← T001:2026-08-05T11:09:58.649Z: JUDGE-DEAD:nonzero-exit MISS 1.7s
```

`recall: 0` И `falsePositiveRate: 0` одновременно — это не «правка ухудшила», это ноль
вынесенных суждений: судья не стартовал ни разу (`nonzero-exit`, стабильно ~1.7 s на кейс,
то есть падение на запуске, а не таймаут).

**Следствие, и оно серьёзное.** `propose` сравнивает `result` с `baseline` и при
`recall 0 < 0.909` штампует `rejected` — при ЛЮБОЙ правке, включая заведомо верную. Гейт,
который должен пропускать улучшения, структурно не может пропустить ничего, пока судья в
бенче не запускается. Отказ записывается в `learnings.jsonl` как содержательный, хотя
измерения не было вовсе.

**Предлагается:** различать «бенч измерил ухудшение» и «бенч не смог измерить». Если доля
`JUDGE-DEAD` выше порога (например 10 %), `propose` обязан возвращать `verdict: "inconclusive"`
и НЕ писать отказ в `learnings.jsonl` — иначе история обучения наполняется отказами,
которые ничего не измеряли.

## D18 — КОРНЕВАЯ причина D17: резолв `claude.exe` не знает нативной раскладки

D17 фиксировал симптом («судья не стартует»). Причина найдена и воспроизведена.

`providers.js:90 claudeExe()` искал ТОЛЬКО npm-раскладку:

```js
const exe = path.join(path.dirname(h), 'node_modules', '@anthropic-ai', 'claude-code', 'bin', 'claude.exe');
```

На машине стоит нативный установщик (CLI 2.1.238): `where claude` отдаёт
`C:\Users\espad\.local\bin\claude.exe` — это УЖЕ настоящий exe, вложенного `node_modules`
рядом нет. Резолв возвращал `null`, дальше по цепочке:

```
resolveBin('claude') → ["claude"]        // fallback
needsShell('claude') → true              // строка не оканчивается на .exe
spawn('claude', argv, { shell: true })   // → cmd.exe
```

`cmd.exe` аргументы НЕ экранирует, а конкатенирует (node сам предупреждает об этом
DEP0190), поэтому JSON схемы разваливался. Воспроизведено напрямую:

```
$ spawn('claude', ['-p','--dangerously-skip-permissions','--json-schema',<json>,'--output-format','json'], {shell:true})
→ exit 1 | Error: --json-schema is not valid JSON: JSON Parse error: Expected '}'
```

Это и есть `JUDGE-DEAD:nonzero-exit ~1.7 s` на всех 58 кейсах: падение на разборе argv,
до обращения к модели.

**Почему дефект был невидим.** Обычные вызовы судьи (`elt commit`) схему не передают —
промпт идёт через STDIN, ломать cmd.exe нечего, вердикты приходят нормальные. Умирает
ровно и только structured-output путь, то есть judge-bench. Комментарий в `providers.js:84-88`
описывает ровно этот класс поломки — его чинили для npm-раскладки, нативный установщик

```js
// `where` уже отдал настоящий exe — берём его как есть.
if (/\.exe$/i.test(h) && fs.existsSync(h)) { _claudeExe = h; break; }
```

## D19 — судья считает scope creep'ом файлы, которые сам гейт признаёт харнесс-владением

В вердиктах T011, T013, T014, T015 повторяется один и тот же упрёк:

```
В .harness/review-queue.jsonl добавлена запись о ... Она не относится к T0NN
и является scope creep текущего слайса.
```

`.harness/review-queue.jsonl` пишет САМ харнесс (`elt review close`), и
`elt-gate-l0.js:185 isHarnessOwned()` явно исключает `.harness/**` из zone-чека. То есть
механический триггер файл не трогает — а LLM-судья, получая сырой дифф, всё равно
объявляет его нарушением границ. Судье не передаётся то знание о владении, которое уже
закодировано в гейте.

**Следствие:** каждый слайс, после которого владелец разобрал очередь предыдущего слайса,
получает ложный упрёк. При этом содержательная часть тех же вердиктов была ВЕРНОЙ и
полезной (T011: «оба кейса проверяют фактический payload… мутация сломает кейс снятия
admin» — точное описание того, что действительно сделано).

**Предлагается:** вычитать харнесс-владения из диффа ПЕРЕД отправкой судье, либо явно
перечислять их в промпте как «не подлежащие оценке».
