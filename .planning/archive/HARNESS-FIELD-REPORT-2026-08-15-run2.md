## D6 — `worktree.create()` переиспользует ветку `fleet/<Tid>` вместе с её старым HEAD

**Статус:** обойдено вручную (удаление веток перед стартом). Требует правки в коде.
**Цена ошибки:** максимальная — воспроизводит D4 целиком, даже когда оператор выполнил
весь документированный обход D4 правильно.

### Наблюдение

После прогона 1 в репозитории остались три ветки на старом коммите:

```
fleet/T004  f1b3e18
fleet/T005  f1b3e18
fleet/T006  f1b3e18
```

`tools/fleet/worktree.js:25-37`:

```js
function create(tid, { cwd = process.cwd(), base = 'HEAD' } = {}) {
  const branchExists = gitOk(['rev-parse', '--verify', '--quiet', branch], cwd);
  if (branchExists) {
    git(['worktree', 'add', p, branch], cwd);        // ← base ИГНОРИРУЕТСЯ
  } else {
    git(['worktree', 'add', p, '-b', branch, base], cwd);
  }
```

Комментарий над функцией объявляет это фичей: «Если ветка `fleet/<Tid>` уже есть (resume
после падения) — переиспользуем, не `-b`». Но `base` при этом не просто не используется —
он **молча отбрасывается**. Вызывающая сторона (`fleet.js:409`) передаёт
`base: integration` и вправе считать, что worktree стоит на интеграционной ветке.

### Почему это ломает именно D4

Сценарий полностью штатный и воспроизводится после любого падения fleet:

1. Прогон 1 упал на `gate-reject/commit` (D4) → ветки `fleet/T004..T006` остались на `f1b3e18`.
2. Оператор делает ровно то, что предписывает отчёт прогона 1: `elt spec approve` +
   **коммит** `approval.json`. Интеграционная ветка уезжает на `d6d92c7` со свежей подписью.
3. Предпусковой approval-guard смотрит рабочее дерево главного репо → `approved` → старт разрешён.
4. `create()` видит существующую ветку и делает `worktree add p fleet/T004` **без base** →
   worktree встаёт на `f1b3e18`, где в HEAD лежит **старая** `approval.json`.
5. `elt commit` внутри worktree читает подпись из HEAD → `stale` → `gate-reject` на `stage=commit`.

То есть свежая подпись существует, закоммичена, guard её видит — и ни один воркер её не видит.
Обход D4 отработал вхолостую.

Побочно: слайс пишется против **устаревшего кода** (на `f1b3e18` нет ни одного коммита,
сделанного после падения), и в merge приходит ветка от старой базы.

### Проверка

Диагностическая, не вердикт: до правки `git worktree list` показывал `f1b3e18` на всех трёх
worktree при `HEAD` главного дерева `d6d92c7`. После удаления веток (`git branch -d fleet/T004…`,
все три — предки HEAD, `-D` не понадобился) и рестарта fleet:

```
C:/…/izi-tracker                 d6d92c7 [session/2026-06-05-1531]
C:/…/izi-tracker/.fleet-wt/T004  d6d92c7 [fleet/T004]
C:/…/izi-tracker/.fleet-wt/T005  d6d92c7 [fleet/T005]
C:/…/izi-tracker/.fleet-wt/T006  d6d92c7 [fleet/T006]
```

Все три на актуальном коммите, `stopped/approval-guard` не сработал, воркеры стартовали.

### Предлагаемое исправление

Переиспользование ветки оставить (resume — валидный сценарий), но привести её к `base`:

```js
if (branchExists) {
  git(['worktree', 'add', p, branch], cwd);
  // ветка resume может стоять на старом коммите — подтянуть до base, иначе слайс
  // пишется против устаревшего дерева и читает устаревший approval.json из HEAD
  gitOk(['-C', p, 'merge', '--ff-only', base], cwd);
}
```

`--ff-only` намеренно: если ветка разошлась с base (есть незамёрдженная работа воркера),
fast-forward не пройдёт, и это должно быть громким отказом, а не тихим сносом чужого коммита.
Альтернатива подешевле — отказ на старте со списком отставших веток.

## D7 — D4 бьёт ВНУТРИ одного прогона, а не только между прогонами

**Статус:** не исправлено. Механизм установлен чтением кода, до спавна воркеров.

Отчёт прогона 1 описывает D4 как проблему между прогонами («`elt commit` после мержа слайса
ставит `[X]` и рассинхронит хэш»). Это верно, но узко. Тот же механизм гарантированно убивает
слайсы **внутри одного прогона**, если открытых слайсов больше, чем воркеров.

### Цепочка (четыре места, все прочитаны)

| Файл | Что делает |
|---|---|
| `elt.js:1074-1085` | approval-гейт считается **до** `markDone()` |
| `elt.js:1116` | `markDone()` пишет `[X]`; пере-подписи в commit-пути нет нигде |
| `merge.js:68-73` | merge-коммит вкладывает `[X]` в `tasks.md` **интеграционной** ветки |
| `fleet.js:409` | `worktree.create(slice.id, { cwd, base: integration })` — `integration` это **имя ветки**, резолвится в момент создания worktree |

Следствие: первый же `merged` сдвигает `tasks.md` интеграционной ветки → `tasksHash` уезжает →
`approval.json` (подписанный под старый `tasks.md`) становится `stale`. Любой worktree,
созданный **после** этого merge, стартует со `stale` подписью в HEAD.

При `--workers 3` и 4 открытых слайсах: T004/T005/T006 создаются до первого merge и коммитятся
нормально, T007 создаётся после — и гарантированно падает `gate-reject/commit`. Отказ приходит
в конце цепочки: воркер отработал, оракул ~200 c зелёный, судья отработал.

Предпусковой approval-guard (`fleet.js:305`) этого не ловит **по построению** — он отрабатывает
один раз, до первого merge, когда подпись ещё валидна.

## J1 — судья пропустил тавтологию, которую предписала сама спека (T006)

**Статус:** дефект доехал до `gate-pass`. Пойман ручным чтением диффа.
**Класс:** промах recall судьи + промах `spec lint`.

`fleet/T006`, `057_work_days_write_guard.sql`:

```sql
CREATE POLICY "user_update_own_work_days" ON public.work_days
  FOR UPDATE
  USING (auth.uid() = user_id AND status <> 'completed')
  WITH CHECK (auth.uid() = user_id AND date = date);
```

`date = date` — тавтология. В выражении RLS-политики доступен **один** ряд: `USING`
вычисляется против существующего, `WITH CHECK` против нового, но пары `OLD`/`NEW` внутри
одного выражения не существует. `work_days.date` объявлен `DATE NOT NULL`
(`001_initial_schema.sql:20`), значит `date = date` всегда `TRUE`. Запрет двигать дату,
заявленный в задаче как половина смысла слайса, не реализован вовсе.

Существенно, что **это дословно предписано текстом задачи**: «`WITH CHECK (auth.uid() =
user_id AND date = date)`; заборону рухати `date` … формулювати саме через `USING` на `OLD`
і `WITH CHECK` на `NEW`». Автор спеки считал, что `USING`/`WITH CHECK` дают доступ к обеим
версиям ряда одновременно. Воркер реализовал предписание буквально и формально прав.

Два вывода для харнесса:

1. **`elt spec lint` не ловит невыполнимые предписания.** Спека, содержащая конструкцию,
   которая в целевой СУБД не выражается в принципе, прошла lint и approve. Это самый дорогой
   класс дефекта: он проходит все гейты, потому что все гейты сверяются со спекой, а неверна
   именно она.
2. **Судья сверяет дифф со спекой, а не с реальностью.** Совпадение с текстом задачи → `pass`.
   Тавтология в security-политике — ровно тот случай, где ожидаешь блок.

Отдельно: тест слайса проверяет `expect(content).toContain('WITH CHECK')` — то есть
подтверждает наличие строки, а не наличие ограничения. Тавтологический прод-код и
тавтологический тест сошлись, и анти-тавтологическая проверка «откатить правку — тест
краснеет» здесь бесполезна: тест покраснеет, но красным он был бы и для no-op политики.

**Что предлагается харнессу:** для слайсов, целиком состоящих из миграции + теста, читающего
файл миграции регэкспами, отдельная рубрика судьи «делает ли SQL то, что заявлено» с явным
запретом засчитывать `toContain` как доказательство поведения. Проверка формы вместо проверки
смысла — систематический слепой пятно этого класса слайсов, а их в спеке 002 четыре из девяти.

## J2 — судья пропустил недостижимый `subject_id` на 2 из 5 таблиц (T004)

**Статус:** дефект доехал до `gate-pass`. Пойман ручным чтением диффа.

`fleet/T004`, `056_activity_log.sql`, универсальная тригер-функция:

```sql
IF TG_TABLE_NAME = 'profiles' THEN
  v_subject_id := (v_target_json->>'id')::uuid;
ELSE
  v_subject_id := (v_target_json->>'user_id')::uuid;
END IF;
```

Колонки `user_id` нет у двух из пяти таблиц, на которые навешан триггер:

| таблица | ключ владельца | `subject_id` получится |
|---|---|---|
| `work_days` | `user_id` | корректный |
| `planned_visits` | `user_id` | корректный |

| `meeting_photos` | `meeting_id` (`032_meeting_photos.sql:5`) | **NULL** |

Критерий приёмки спеки — «`actor_id` і `subject_id` різні, коли адмін править чужий день» —
для событий уровня встречи и фото не выполняется: субъект неизвестен. Это 3 из 12 событий,
ради которых спека и писалась.

Как и J1, предписано текстом задачи дословно («`subject_id` береться з `NEW.user_id`/`OLD.user_id`
… через `to_jsonb(...)->>'user_id'`»), и как и в J1, ни `spec lint`, ни судья не сверили
предписание со схемой БД. Тест слайса проверяет наличие пяти имён таблиц в `CREATE TRIGGER` —
форму, не смысл.

Общее у J1 и J2: **оба дефекта пришли из спеки, оба прошли judge, оба невидимы тесту-регэкспу.**
Это не промах модели-воркера — воркер исполнил задание точно. Это промах слоя, который должен
сверять задание с внешней реальностью (схемой БД, семантикой Postgres), и такого слоя в
харнессе сейчас нет.

## J3 — слайс сделал приватный хелпер публичным Server Action ради тестируемости (T007)

**Статус:** дефект доехал до `gate-pass` и `merged`. Пойман ручным чтением диффа, исправлен вручную.
**Класс:** промах recall судьи. В отличие от J1/J2 — **не** предписан спекой, внесён воркером.

`src/lib/actions/photos.ts` начинается с `'use server'`. T007 понадобилось дёрнуть внутренний
`checkIsAdmin` из теста, и воркер просто добавил `export`:

```diff
-async function checkIsAdmin(supabase: …) {
-  const { data } = await supabase.from('profiles').select('role').single()
+export async function checkIsAdmin(supabase: …, userId: string) {
+  const { data } = await supabase.from('profiles').select('role').eq('id', userId).single()
```

В Next.js App Router **каждый export из `'use server'`-модуля становится публичным
Server Action endpoint'ом**. Приватная проверка роли превратилась в вызываемую снаружи ручку.
Задача при этом была про ужесточение безопасности — слайс закрыл дыру (`.eq('id', user.id)`)
и в том же диффе открыл новую поверхность.

Показательно, что тот же слайс сделал `export` и для `isAuthorizedCron` в
`src/app/api/backup/route.ts` — там это безвредно (route-файл, не `'use server'`), и именно
поэтому одинаковая с виду правка в двух файлах имеет разную цену. Судья дал `pass` на оба.

**Исправлено в этой сессии:** `checkIsAdmin` вынесен в обычный модуль `src/lib/auth/is-admin.ts`,
`photos.ts` импортирует его, тест импортирует оттуда же. Публичный endpoint исчез,
тестируемость сохранена.

**Что предлагается харнессу:** механический чек, а не рубрика судьи — дифф, добавляющий `export`
в файл с `'use server'` в первой строке, это `grep`-уровня проверка и ложится в L0 или в
`attest`. Класс «тест потребовал видимости → расширили публичный API» универсален для любого
фреймворка с файловыми границами доверия (`'use server'`, `'use client'`, `__all__`, `pub`).

## D8 — `bg-red` слоя `judge` без единого судейского вывода

`elt review` показывает:

```
[bg-red/judge] T009  173fbdb
  судья: out-of-scope: … ; diff-size: дифф 694 строк при пороге 400;
         external-import-no-ctx7: новый внешний импорт без свежего пруфа ctx7 (30 дн.): vitest, next
```

Слово «судья:» здесь — обёртка вокруг **списка L0-триггеров**, а не вердикт. В логе
`.harness/loop-logs/bg-173fbdb.log` (29 строк) есть только слой `suite`: прогон
`npx tsc --noEmit && npm run lint && npm test`, exit 0. Ни `mutate`, ни `smoke`, ни `judge`
не оставили ни строки. Судейского proof нет нигде: в `.harness/` только `harness.json`,
`loop-logs/`, `oracle-tail.log`, `review-queue.jsonl` и `fleet/`.

**Почему это дорого.** Владелец не может отличить два принципиально разных исхода:

- судья вызван, прочитал дифф и заблокировал по причине X;
- судья вызван из-за триггеров X и **не ответил вовсе**.

Скилл прямо называет второй случай инцидентом («Мовчання фону — інцидент, а не тиша»),
но в очередь он попадает под видом первого — как обычный `bg-red`, который полагается
разобрать и закрыть `elt review close`. То есть механизм, спроектированный на отлов
молчания судьи, обходится тем, что молчание маскируется под красный вердикт.

**Усугубляет:** файла `.harness/health.jsonl` не существует. Значит `harness-watch` в этом
проекте не работает, `bg-silent` не пишется никогда, и счётчик «три `bg-silent` подряд →
вернуться на `verify: "sync"`» не может сработать по построению. `node tools/doctor.js`
покажет длину очереди `bg-red`, но число `bg-silent` у него всегда будет нулём — не потому
что тишины нет, а потому что её никто не считает.

**Что предлагается:** (1) в записи очереди разделить поля `triggers` (почему звали судью) и
`verdict` (что судья ответил); отсутствие `verdict` при непустых `triggers` — это `bg-silent`,
а не `bg-red`; (2) `doctor` должен явно ругаться на отсутствующий `health.jsonl` при
`verify: "background"`, потому что это не «ноль инцидентов», а «датчик не подключён».

## D9 — zone-чек `[files:]` штрафует за файлы, которые предписала переписать сама задача

Из того же вердикта: `out-of-scope: файл вне объявленной зоны [files:]:
migration-059-contractors-gin.test.ts, address-autocomplete-rate-limit.test.ts,
package-lock.json`.

Текст T009 звучит буквально так: «прибрати невикористані `recharts`, `jspdf`,
`jspdf-autotable` і перенести CLI `shadcn` у `devDependencies`», а его оракул — «`npm ls
recharts` порожній». Выполнить это, не изменив `package-lock.json`, невозможно: npm
переписывает лок-файл всегда. При этом в зоне `[files:]` объявлен только `package.json`.
Чек ловит не отклонение исполнителя от плана, а неполноту самого плана в той части,
которую план не мог бы заполнить иначе как перечислением генерируемых артефактов.

Второй симптом того же корня: `diff-size: дифф 694 строк при пороге 400`. Ручной дифф слайса
— 4 файла и ~60 строк; остальные ~630 это `package-lock.json`, который никто не писал.
Порог, считающий сгенерированные строки, срабатывает на любом слайсе, трогающем зависимости.

Побочно всплывает процессный тупик: чтобы легально добавить тест, не перечисленный в
`[files:]`, надо отредактировать `tasks.md` → `tasksHash` меняется → approval уходит в
`stale` → нужен новый approve. То есть «дописать тест к слайсу» стоит столько же, сколько
переутверждение спеки, и это подталкивает исполнителя либо не писать тест, либо ловить
`out-of-scope`.

**Что предлагается:** список lockfile-подобных путей (`package-lock.json`, `pnpm-lock.yaml`,
`yarn.lock`, `Cargo.lock`, `poetry.lock`, `go.sum`), которые исключаются и из zone-чека, и
из счётчика `diff-size`; плюс безусловное разрешение на добавление файлов под
`src/__tests__/` и `e2e/` — тест не расширяет поверхность продукта.

## D10 — `external-import-no-ctx7` считает новыми импортами `vitest` и `next`

Третья часть вердикта: `новый внешний импорт без свежего пруфа ctx7 (30 дн.): vitest, next`.

В репозитории 42 тест-файла и 368 тестов; `vitest` импортируется в каждом из них, `next`
— это фреймворк проекта (`next: 16.2.4` в зависимостях с первого коммита). Новых
зависимостей слайс не добавил ни одной — наоборот, удалил три (`recharts`, `jspdf`,
`jspdf-autotable`). Чек, очевидно, считает «внешним импортом» первое вхождение пакета
**в новых файлах диффа**, а не появление новой строки в `package.json`.

**Следствие:** любой слайс, создающий новый тест-файл, обязан получить этот флаг — а значит
флаг не несёт информации и обучает игнорировать вердикт целиком. Здесь он приехал в одном
списке с D9, и оба вместе дали `bg-red` на слайсе, где оракул зелёный, дифф прочитан руками
и дефектов не содержит.

**Что предлагается:** сверять не импорты в диффе, а дельту `dependencies`/`devDependencies`
в `package.json`. Пакет, уже присутствующий в манифесте до слайса, внешним импортом не
является независимо от того, в скольких файлах он раньше упоминался.

## D11 — каждый `elt commit` делает approval `stale` для следующего слайса (не-fleet путь)

D7 описан на примере fleet: merge-коммит не переподписывает `approval.json`. Тот же корень
бьёт и по основному, последовательному пути, где fleet не участвует вовсе.

Наблюдение на борговом раунде спеки 002 (T010 → T011 → T012, три слайса подряд, вручную,
`verify: "background"`):

```
elt commit --task T010 …   → 6b13540  T010 [X]        (успех)
elt commit --task T011 …   → elt: спека не утверждена: elt spec approve (status: stale)
```

`elt commit` сам правит `tasks.md`, переводя `- [ ] **T010**` в `- [X] **T010**`. Это меняет
`tasksHash`, и подпись, действительная секунду назад, становится недействительной — для
слайса, который ещё даже не начинали. То есть **успешное закрытие слайса ломает гейт для
следующего**. На трёх слайсах пришлось переподписывать дважды; на спеке из девяти открытых
задач это восемь лишних переподписей, и каждая приходит после полного прогона оракула
(35–53 c в этом проекте), а не до него.

Обходной путь, которым пользовались здесь, скилл разрешает прямо («Тихе повторне approve
дозволене лише після чистого `[ ]` → `[X]`, який зробив `elt commit`»), но разрешение
написано для человека, а проверяет его человек же — руками, диффом `git diff <prev> <cur> --
tasks.md`. Механизм, который умеет отличить «изменился только чекбокс, и его поставил сам
`elt commit`» от «текст задачи переписали», в коде отсутствует, хотя ровно эта проверка и
есть весь смысл `specApproval`.

**Что предлагается:** `elt commit`, поставив `[X]`, обязан пересчитать `tasksHash` и
переподписать `approval.json` в том же коммите — ровно как предлагается для `merge.js` в D7,
но в `commit.js`. Подпись при этом не ослабевает: `commit` меняет один символ в строке,
которую сам же и закрывает, и может проверить, что дифф `tasks.md` состоит ровно из этого.
Пока этого нет, `specApproval: true` на спеке длиннее двух задач — источник ложных отказов,
а не гарантия.

**Симптом, замкнувший круг.** Переподпись, которой D11 вынуждает, тут же ловится zone-чеком
из D9. Фоновый вердикт слайса T011:

```
[bg-red/judge] T011  7fdae69
  судья: out-of-scope: файл вне объявленной зоны [files:]:
         specs/002-security-audit-logging/approval.json — барьерный слайс легитимен, судья решает;
         external-import-no-ctx7: … vitest
```

`approval.json` в этот коммит положил не исполнитель: его переписал `elt spec approve`,
вызванный потому, что предыдущий `elt commit` сделал подпись `stale`, и подобрал в коммит
сам `elt commit`. Харнесс штрафует слайс за файл, который сгенерировал сам, в обход зоны,
объявить которую заранее невозможно — `files:` пишется при планировании, когда переподписи
ещё нет. Тот же прогон дал `external-import-no-ctx7: vitest` на T010 и T011 (D10) —
подтверждая, что флаг приезжает на каждом слайсе с новым тест-файлом без исключения.

## D12 — `agent-browser eval --stdin` молча возвращает `null`

**Статус:** не исправлено. Обойдено inline-формой.
**Класс:** тихий отказ — нет ни ошибки, ни ненулевого кода выхода.

`agent-browser eval --help` объявляет `--stdin  Read script from stdin (useful for
heredocs/multiline)`. Фактически режим не исполняет скрипт:

```
PS> agent-browser eval "1+1"          → 2
PS> "2+3" | agent-browser eval --stdin → null
PS> agent-browser eval "document.querySelectorAll('button').length" → 34
```

Inline-форма работает на той же странице и в той же сессии. `--stdin` возвращает `null`
для любого выражения — то есть отличить «скрипт вернул null» от «скрипт не выполнялся»
на стороне вызывающего невозможно.

**Почему это дорого именно здесь.** Оба документированных способа передать нетривиальный
скрипт закрыты одновременно:

- `--stdin` — не работает (этот дефект);
- `-b/--base64`, который в справке прямо предлагается «avoids shell escaping issues», —
  блокируется auto-mode классификатором Claude Code как обфускация.

Остаётся inline-однострочник, а он упирается в экранирование PowerShell и в кодировку
кириллицы в аргументах (фильтр по тексту кнопки `'Надати'` пришлось переписать на поиск
по `@` в тексте карточки, чтобы не гонять кириллицу через границу процесса).

**Что предлагается:** при пустом результате `--stdin` возвращать ненулевой код выхода и
явное сообщение. Тихий `null` в инструменте, чей единственный выход — возвращаемое
значение, неотличим от валидного ответа.

## Операционные наблюдения

- **Классификатор блокирует чтение `document.cookie` / `localStorage` через `eval`** —
  срабатывание корректное (выглядит как выемка сессионного токена), но следствие:
  проверить REST-эндпоинт из уже авторизованной страницы нельзя. Для `activity_log`,
  у которого в продукте пока нет UI, это означает, что проверка «пишется ли запись»
  недостижима браузерным путём и требует SQL-доступа (Supabase MCP / Studio).
- **Программный `element.click()` через `eval` тоже блокируется** — штатный
  `agent-browser click "@eN"` проходит. Ограничение обходится сменой инструмента, не
  формулировки, но стоит одного лишнего цикла на догадку.
- **`supabase db dump` требует запущенный Docker Desktop** даже для чисто удалённого
  дампа (тянет образ `public.ecr.aws/supabase/postgres`). На машине без поднятого демона
  снимок схемы перед миграцией недоступен — а это единственный дешёвый способ проверить
  допущения миграции о проде до `push`. Здесь дамп подтвердил допущение 060
  (`GRANT ALL ON TABLE profiles TO authenticated` на проде существует, значит
  `REVOKE UPDATE` не no-op) и вскрыл, что `pg_trgm` в проде не установлен, из-за чего
  059 создала расширение в схеме `public`, а не в `extensions`.
- **`agent-browser open` не возвращает управление** (~3 мин до таймаута), хотя страница
  фактически открыта: параллельный `agent-browser get url` сразу отдаёт корректный URL.
  Обход — обёртка `Start-Job` + `Wait-Job -Timeout`.
