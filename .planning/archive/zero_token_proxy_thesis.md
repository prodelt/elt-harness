# Инженерный тезис: Zero-Token Proxy (Validated PoC Thesis)

## 1. Executive verdict

- **Подтверждено:** Prompt caching у Anthropic действительно работает по принципу точного префикса. Кэш читается только если префикс до брейкпоинта совпадает на 100%.
- **Подтверждено с уточнением:** Любое изменение в блоках до `cache_control` меняет cumulative hash префикса и ломает hit для этого брейкпоинта. При этом система читает только те позиции, которые уже были записаны предыдущими запросами.
- **Опровергнуто как unsafe-допущение:** “Свободно переставлять блоки внутри `messages` без влияния на семантику” нельзя. Для `tool_result` и `thinking` у Anthropic есть строгие требования к порядку и целостности.
- **Скорректированный вывод:** жизнеспособен только **Safe Injection Proxy**, который не меняет порядок смысловых блоков и не пытается “оптимизировать” историю диалога перестановками.
- **Реалистичная цель PoC:** не “гарантировать 90% попадание в кэш”, а прозрачно добавлять корректный cache breakpoint в стабильный текстовый блок и проксировать SSE без деградации ответа.

## 2. Проблема

Автономные coding-агенты часто шлют в Anthropic большой повторяющийся контекст без явного cache breakpoint. В результате длинные system prompts, tool definitions и большие текстовые блоки повторно тарифицируются как обычный input, хотя могли бы читаться из prompt cache.

Изначальный тезис верно нащупал проблему, но делал слишком сильное предположение: будто можно безопасно “переупаковывать” `messages` и сдвигать “горячие” куски вниз. По официальной документации Anthropic это рискованно, потому что:

- порядок `tools -> system -> messages` участвует в кэш-иерархии;
- `tool_result` должен идти сразу после `tool_use` и стоять первым в user content array;
- `thinking` блоки при tool use нужно возвращать обратно без изменений и без перестановки.

## 3. Валидация по официальной документации Anthropic

### Вопрос 1. Привязан ли кэш к префиксу?

**Ответ: да.**

Anthropic прямо пишет, что prompt cache ссылается на полный префикс `tools`, затем `system`, затем `messages` вплоть до блока с `cache_control`. Также документация уточняет, что при explicit breakpoint записывается ровно один cache entry: хэш накопленного префикса до этого блока. Если любой блок на пути до брейкпоинта меняется, на следующем запросе получается другой хэш, и hit исчезает.

Практическое следствие:

- если динамический timestamp лежит до брейкпоинта, этот брейкпоинт становится бесполезным;
- брейкпоинт нужно ставить на **последний стабильный блок**, а не на просто “самый поздний” блок.

### Вопрос 2. Можно ли свободно переставлять блоки в `messages`?

**Ответ: как общую стратегию — нет.**

Формально Anthropic API допускает массивы content blocks, но семантическая перестановка истории не является безопасной оптимизацией. Документация фиксирует как минимум три ограничения:

- `tool_result` должен идти сразу после соответствующего `tool_use`;
- внутри user message `tool_result` блоки должны быть первыми;
- `thinking` блоки при tool use нужно возвращать обратно полностью и без модификаций.

Следствие для архитектуры:

- безопасно добавлять `cache_control` в существующий блок;
- небезопасно перестраивать порядок user/assistant turns;
- небезопасно перемещать “статус терминала”, “время” или другие куски текста между сообщениями без доказанной семантической эквивалентности.

### Вопрос 3. Как использовать лимит в 4 breakpoint'а?

**Ответ: только если это действительно нужно.**

Anthropic пишет, что одного breakpoint в конце стабильного префикса часто достаточно. Несколько breakpoint'ов нужны, когда:

- разные секции меняются с разной частотой;
- история уходит дальше окна lookback в 20 блоков;
- нужно кэшировать длинные секции независимо друг от друга.

Рекомендуемая раскладка для agent-style payload:

1. `tools` — если список инструментов тяжелый и редко меняется.
2. `system` — если system prompt стабилен между вызовами.
3. Большой reusable context — например, длинный code snapshot или загруженный документ.
4. Дополнительный checkpoint ближе к хвосту только если разговор вырастает так, что прошлый cache write уходит за 20-блочное окно lookback.

Для PoC достаточно **одного explicit breakpoint** на самом длинном стабильном текстовом блоке.

## 4. Архитектурные варианты

### Вариант A. Aggressive Reorder Proxy

- Прокси пытается делить контекст на “холодный” и “горячий”.
- Переставляет блоки внутри `system/messages`, чтобы статичный префикс был выше.
- Потенциально дает лучший cache hit rate.

**Почему отклонено:** высокий риск сломать tool loops, thinking continuity и семантику разговора.

### Вариант B. Safe Injection Proxy

- Прокси не меняет смысловой порядок сообщений.
- Находит лучший кандидат для explicit breakpoint.
- Иммутабельно добавляет `cache_control` в один текстовый блок.
- Затем прозрачно проксирует запрос и SSE-ответ.

**Почему выбран:** минимальный риск, прозрачность для агента, достаточность для PoC.

### Вариант C. Client-Native Integration

- Кэширование добавляется прямо в самом агенте или SDK-клиенте.
- Можно использовать top-level automatic caching или explicit block-level caching.

**Почему не выбран для PoC:** требует менять клиента. Текущая задача — проверить MITM-подход без модификации агента.

## 5. Выбранная архитектура PoC

PoC реализуется как локальный reverse proxy на Node.js без внешних зависимостей:

- слушает `PORT` (по умолчанию `8080`);
- принимает `POST /v1/messages`;
- валидирует базовую форму payload;
- ищет самый длинный text block в `system` и `messages`;
- если в нем еще нет `cache_control` и лимит брейкпоинтов не исчерпан, добавляет `{ "type": "ephemeral" }`;
- пересылает модифицированный JSON в `https://api.anthropic.com/v1/messages`;
- прозрачно возвращает upstream response, включая streaming/SSE.

Почему Node.js для PoC:

- в проекте уже базовый стек на Node.js;
- `fetch`, Web Streams и `http` доступны из коробки в текущем Node;
- можно сделать zero-dependency proxy и не тащить Express/FastAPI ради минимального эксперимента.

## 6. Нефункциональные ограничения

PoC **не должен**:

- переставлять user/assistant messages;
- трогать `tool_use`, `tool_result` или `thinking` блоки как структуру;
- обещать cache hit там, где до брейкпоинта есть динамические данные;
- ломать SSE streaming или скрывать upstream ошибки.

PoC **должен**:

- быть прозрачен для клиента;
- работать иммутабельно, без мутации входного объекта;
- логировать структурированно;
- возвращать предсказуемую JSON-ошибку вида `{ error, code, details }`.

## 7. Алгоритм Safe Injection

1. Прочитать тело запроса и распарсить JSON.
2. Проверить, что `messages` — это массив.
3. Нормализовать `system` и `message.content` в массивы блоков только там, где это нужно для инъекции.
4. Собрать все top-level text blocks из `system` и `messages`.
5. Выбрать самый длинный текстовый блок.
6. Если блок уже имеет `cache_control`, ничего не менять.
7. Если уже есть 4 explicit breakpoint'а, сделать no-op и просто проксировать исходный payload.
8. Иначе создать новый payload с добавленным `cache_control` только в выбранный блок.
9. Отправить запрос в Anthropic.
10. Пробросить status, headers и response stream обратно клиенту.

## 8. Проверка успеха PoC

PoC считается успешным, если:

- агент продолжает работать без знания о proxy;
- SSE-стрим не ломается;
- upstream поведение совпадает с прямым вызовом, кроме появления cache metadata;
- в `usage` начинают появляться `cache_creation_input_tokens` и затем `cache_read_input_tokens`, когда префикс реально стабилен.

PoC не считается успешным, если:

- ответы модели деградируют из-за перестановки смысла;
- tool loop начинает падать на ошибках формата;
- proxy создает новые cache writes, но почти никогда не получает cache reads.
