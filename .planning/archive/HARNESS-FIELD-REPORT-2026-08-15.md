## 2. Дефекты

### D1 — worktree без `node_modules`: оракул любого JS-проекта красный по построению

**Статус:** исправлено (`tools/fleet/worktree.js`).

`git worktree add` не переносит неотслеживаемое, а `node_modules` в `.gitignore`. Свежий
worktree воркера пуст → `npx tsc`, `npm run lint`, `npm test` падают с «нет зависимостей».
Гейт читает это как красный оракул слайса. Для любого Node-проекта fleet был неработоспособен
до первой строки кода воркера.

Правка: `linkNodeModules()` вешает симлинк-junction на `node_modules` корня при создании
worktree. На Windows junction не требует прав администратора, на POSIX — обычный dir-симлинк.

Известный потолок (помечен `ponytail:` в коде): линк общий на все worktree, параллельные
vitest/eslint делят кэш внутри `node_modules`. За прогон гонок кэша не наблюдалось. Апгрейд,
если появятся: `npm ci` в каждый worktree (минуты на слайс) или per-worktree cache dir через
env оракула.

**Проверено:** оракул в чистом worktree — `exit 0`, 340/340, 209 c.

### D2 — удаление worktree шло СКВОЗЬ junction и выедало корневой `node_modules`

**Статус:** исправлено (`tools/fleet/worktree.js`). Регрессия, внесённая правкой D1.

`removeWorktreeRetrying()` после неудачи `git worktree remove` падает в
`fs.rmSync(p, {recursive: true, force: true})`. На Windows этот вызов пошёл **внутрь**
junction и начал удалять содержимое `node_modules` **корневого дерева**: первым лёг
`node_modules/.bin` (пустой каталог вместо 117 бинарей), затем удаление упёрлось в залоченный
файл и отрапортовало «директория занята другим процессом» — то есть настоящая причина была
замаскирована сообщением о локе.

Опасность класса «тихая порча вне зоны работ»: сообщение об ошибке указывает на worktree, а
разрушается главное дерево. Заметно только по внезапно красному оракулу «на ровном месте».

Правка: `unlinkNodeModules()` снимает линк **до** любого удаления — и утечка удаления, и сам
источник лока исчезают.

**Восстановление:** `npm ci` не прошёл (EPERM на `lightningcss.win32-x64-msvc.node`, файл
держал живой процесс), `npm install` восстановил дерево. `package-lock.json` не изменился,
оракул главного дерева снова зелёный 340/340.

### D3 — `attest.js`: честная заявка на новый тест читалась как `undeclared-file`

**Статус:** исправлено (`tools/fleet/attest.js`) + регресс-тест (`attest.test.js`).

Контракт воркера требует закончить ответ заявкой
`{"filesChanged":[...],"testsAdded":[...]}`. Сверка была асимметричной:

```js
const claimed = [...new Set([...claim.filesChanged, ...claim.testsAdded])]; // union
const hallucinated = claimed.filter((f) => !actual.includes(f));            // ← union
const undeclared  = actual.filter((f) => !claim.filesChanged.includes(f));  // ← только половина
```

Новый тест, положенный воркером в `testsAdded` **ровно как требует промпт**, попадал в
`undeclared`. Итог: **19 отказов из 20 подряд**, и в каждом `detail` — ровно один файл, всегда
новый тест:

```
3 "detail":["src/__tests__/lib/migration-057-work-days-guard.test.ts"]
3 "detail":["src/__tests__/lib/migration-056-activity-log.test.ts"]
3 "detail":["src/__tests__/lib/migration-055-role-guard.test.ts"]
3 "detail":["src/__tests__/lib/import-pagination.test.ts"]
3 "detail":["src/__tests__/api/middleware-api-bypass.test.ts"]
3 "detail":["src/__tests__/actions/auth-activity.test.ts"]
1 "detail":["src/__tests__/actions/hygiene-002.test.ts"]
```

Любой слайс с новым тестом был непроходим в принципе — какой бы моделью ни писался. Проектная
дисциплина «слайс закрывается тестом» и механика attest противоречили друг другу.

Правка: `undeclared` сверяется с тем же `claimed`, что и `hallucinated`.

**Доказательство, а не вердикт:** добавлен тест `новый тест в testsAdded не считается
незаявленным`. Со старым кодом — красный (`✖ pass 0 / fail 1`), с новым — зелёный,
`attest.test.js` 18/18.

### D4 — approval-guard проверяет рабочее дерево, а воркер читает HEAD

**Статус:** не исправлено, обойдено вручную. Требует решения владельца.

`fleet.run()` имеет предпусковой approval-guard и честно отказывается стартовать при
`status: stale` (`stoppedReason: "approval-guard"`, наблюдалось). Но guard смотрит **рабочее
дерево главного репо**, а `elt commit` внутри worktree читает `approval.json` из **HEAD**.
Незакоммиченная переподпись даёт расхождение: guard пропускает прогон, а каждый слайс падает
в самом конце цепочки:

```json
{"event":"gate-reject","tid":"T001","stage":"commit",
 "err":"elt: спека не утверждена: elt spec approve (status: stale, ...)"}
```

Цена ошибки максимальная: воркер отработал, оракул зелёный (≈200 c), судья отработал (до 8 мин),
и только потом commit отказывает — **9 отказов, три слайса abandoned**, весь LLM-бюджет раунда
сожжён.

Сценарий воспроизводится штатно: `elt commit` после мержа слайса ставит `[X]` и рассинхронит
хэш `tasks.md` → следующий `elt spec approve` создаёт незакоммиченный `approval.json` → все
последующие слайсы гарантированно не закоммитятся.

**Предлагаемое исправление** (одно из):
1. approval-guard сверяет подпись **в HEAD интеграционной ветки**, а не в рабочем дереве;
2. либо fleet отказывается стартовать при незакоммиченном `approval.json` с явным
   сообщением «подпись не в HEAD — воркеры её не увидят».

Второе дешевле и честнее: отказ до спавна вместо отказа после.
