# ELT-CODE (A) — дизайн + план сборки

> Статус: согласовано в grill-сессии 2026-06-20. Это спека режима **coding-engineering**.
> Метод: тонкий слой-вход поверх существующего (`/pipeline`, `/project-bootstrap`,
> `harness-method`, PLAYBOOK), НЕ новая система. Анти-AMOS: ничего не инжектится per-turn,
> конфиг per-project, «Done» только с proof.

## Рамка

- Два режима в перспективе: **`/elt-code`** (разработка софта) и **`/elt-work`** (повседневка/компания).
  Сейчас строим **только `/elt-code`**. `/elt-work` — после успешной реализации кодинг-режима.
- Внутри `/elt-code` две цели по порядку:
  - **A — надёжный прогон каждый раз** (судья-гейт + надёжный вход). Строим сейчас.
  - **B — eval-флайвил** (система измеряет и улучшает себя). Потом. Заводится на данных, что копит A.
- **Шов A→B** = лог судьи (`judge_verdict` в session-ledger). Накопленные вердикты = eval-корпус для B.

## Дизайн (A) — 8 узлов

### 1. Спина `/elt-code`
Intent-роутер с меню как fallback. `/elt-code "почини логин"` → сразу едет. Голый `/elt-code` →
меню из 6 интентов (грузит последний checkpoint для «продолжить роадмап»). Читает интент → ставит
код-контекст on-demand → диспетчит. Классификацию по сложности отдаёт `/pipeline`, не дублирует.
Интент (что за сессия) и сложность (насколько тяжёлый маршрут) — ортогональны.

### 2. Контекст входа (on-demand, без хука)
При вызове `/elt-code`: читает `pipeline-state.json` + последний `/checkpoint` + один таргетированный
`mem-search` по активному проекту. **Никакого SessionStart-хука** (это рецидив AMOS №1). Граф
(codegraph) — query-on-demand, НЕ пре-грузится в контекст. Существующий лёгкий session-start
(claude-mem recent-obs + auto-memory MEMORY.md) оставляем как есть.

### 3. Диспетчер (6 интентов → существующие скилы)
| Интент | Маршрут |
|---|---|
| Продолжить роадмап | checkpoint + `.planning/` → следующий пункт в `/pipeline` |
| Новая фича / крупное | `/pipeline` + spec-kit (полный стек, узел 4) |
| Багфикс | `/pipeline` (BUG) → `diagnose` → судья |
| E2E + QA | `qa` + `agent-browser` (единственный браузер) |
| Аудит качества | **судья standalone** + `ponytail-audit` + `performance-optimization` + `improve-codebase-architecture` |
| Security red/blue | `security-best-practices` (blue) сейчас; **red-team — отложен** |

`/elt-code` — тонкий диспетчер поверх готового, НЕ фабрика агентов.

### 4. Слои реализации (масштабируются по сложности `/pipeline`)
Полный стек для COMPLEX (MEDIUM — подмножество, TRIVIAL — почти ничего):
`spec-kit → ctx7 → architect-first → tdd/sprint → inline-review → СУДЬЯ → lint/test/типы (pipeline
closeout) → security-best-practices → ship`. Новое тут — только **Spec-слой** и **судья**; остальное —
секвенирование существующего.

### 5. Spec — spec-kit, per-project
Установка `specify init` в репо (кладёт команды в `.claude/`), НЕ глобально. Фазы по сложности
(перило I): COMPLEX = полный флоу, MEDIUM = `specify→plan→implement`, TRIVIAL пропуск.
spec-kit генерирует, **судья H1 enforce'ит** (перило II). `constitution.md` = принципы проекта **+**
секция расширений рубрики судьи (один файл, два назначения, оба per-project). spec-kit кросс-агентный —
обслуживает кросс-CLI (узел 8) и анти-вайбкодинг по конструкции (цель «уход от вайбкодинга»).

### 6. Судья — гибрид (сердце A, недостающий пункт)
**Роль:** не ревьюер (находит проблемы), а судья (ставит вердикт по рубрике, измеримо).

**Твёрдый пол (блокирует, бинарно):**
- **H0** (предусловие, переиспользуем): `/pipeline` closeout прошёл — тесты/линт/секреты.
- **H1**: спека реализована (что в `spec.md`/задаче — то сделано, не больше).
- **H2**: нет оверинжиниринга — `ponytail-audit` чист.

**Мягкое качество (советует 1-5 + коммент, логируется, НЕ блокирует):**
- **S1** читаемость/нейминг · **S2** структура/размещение · **S3** консистентность с кодовой базой ·
  **S4** качество тестов.

**Модель:** отдельный субагент, **Sonnet** дефолт, **Opus** на COMPLEX/высоких ставках. НЕ haiku, НЕ
self-judge. Единственное место, где на модели не экономим — слабый судья = ложная уверенность.

**Когда:** только код-интенты. TRIVIAL и не-код пропускают. MEDIUM+ = вердикт на closeout. COMPLEX =
вердикт на каждый sprint-слайс.

**Второй вход:** standalone = интент «аудит качества» (судья без задачи, по существующему коду).

**Лог:** `judge_verdict` в существующий `session-ledger.jsonl` (новый стор НЕ заводим) = **шов к B**.

**Кросс-CLI:** в Claude — субагент; в Codex/Antigravity — инлайн (та же рубрика, тот же ledger).

### 7. Знание/память — файлово-центрично (аддитивно)
Источник правды для ВСЕХ трёх CLI = **файлы**: `spec.md` + `constitution.md` (рубрика) +
`session-ledger.jsonl` (лог судьи) + `memory/*.md`. Per-project файлы в репо (версионируются, ездят с
проектом) + тонкий глобальный индекс (как уже есть: `~/.claude/projects/<key>/memory/MEMORY.md`).
claude-mem + субагенты = **Claude-ускорители поверх**, аддитивно — **в Claude всё работает 1:1 как
сейчас**, ничего не выпиливаем. claude-mem — не стор правды, а ускоритель на Claude-стороне.

### 8. Упаковка — скилы, не плагины
`/elt-code` — **скил** (markdown), зеркалится в `~/.codex/skills` + `~/.gemini/skills` существующим
механизмом. Плагин не берём: Claude-Code-специфичен, не портируется, бандлить нечего (хуков не делаем).
spec-kit кросс-агентный. Codex/Antigravity: судья инлайн, читают те же файлы → консистентно.

**Жёсткая правда (принято явно):** авто-захват claude-mem и изоляция субагентами — только Claude.
Кросс-CLI едет общее ЗНАНИЕ (файлы) + общий ПРОЦЕСС (скилы + spec-kit + рубрика), не Claude-механика.
Это апгрейд с нуля для Codex/Antigravity (сегодня у них ноль общего знания), а не даунгрейд Claude.

## План сборки

Принцип фазирования: ценность вперёд + зависимости. Каждая фаза — самостоятельно ценна и закрывается
**proof** (вывод команд / live-fire, не «готово»).

### Фаза 0 — Скелет + диспетчер `/elt-code`
- Скил `~/.claude/skills/elt-code/SKILL.md`: детект интента из сообщения + меню-fallback при голом вызове.
- Контекст входа on-demand: `pipeline-state.json` + последний checkpoint + один `mem-search`.
- Таблица диспетчеризации (6 интентов → существующие скилы).
- **Proof:** `/elt-code "fix X"` → роутит в `/pipeline`; голый `/elt-code` → меню; не-код интент (QA) →
  `qa`+`agent-browser`. Без судьи пока. Даёт сразу: единая дверь.

### Фаза 1 — Судья-субагент (сердце, наибольшая ценность)
- Базовая рубрика H0-H2 + S1-S4 в скилле.
- Судья = Sonnet-субагент: читает изменённые файлы + spec + рубрику → вердикт (блок на твёрдом полу /
  совет+лог по мягкому). H2 = вызов `ponytail-audit`; H0 = pipeline closeout; H1 = spec-чек.
- Вшить в closeout (MEDIUM+) и per-слайс (COMPLEX) через `/pipeline`/`sprint`.
- Лог `judge_verdict` → `session-ledger.jsonl`.
- Standalone-режим = интент «аудит качества».
- Скил написан так, что в не-Claude работает инлайн (без спавна субагента).
- **Proof:** live-fire — реальное изменение: показать блок-кейс (H1 спека не совпала → blocked) и
  совещательный кейс (S-оценки в логе); показать строку `judge_verdict` в ledger.

### Фаза 2 — Интеграция spec-kit
- `specify init` per-project (задокументировать ритуал; опционально — шаг в `/project-bootstrap`).
- Конвергенция `constitution.md` (принципы + секция рубрики).
- Вшить H1: проверка adherence против `spec.md`.
- Фазы по сложности (перило I).
- **Proof:** COMPLEX-задача → `spec.md` → тесты из критериев приёмки → судья H1 сверяет; показать трассу
  spec→test→adherence.

### Фаза 3 — Кросс-CLI зеркало
- Зеркалить скил `/elt-code` в `~/.codex/skills` + `~/.gemini/skills`.
- Проверить, что файловый источник правды читается в Codex (судья инлайн).
- **Proof:** тот же `spec`/рубрика/ledger читаются из Codex; судья отрабатывает инлайн там.

### Фаза 4 — Проверка шва к B (не сам B)
- Подтвердить, что `judge_verdict` копятся по прогонам в ledger'ах.
- Тонкий глобальный индекс на них (переиспользовать существующий паттерн памяти).
- **Proof:** N прогонов → N событий `judge_verdict` читаемы — это семя eval-корпуса для будущего B.

## Уточнения (gap-review 2026-06-20)

Найдено при проверке «ничего ли не упустил» — закрыто здесь:

1. **Источник H1 (спека реализована):** если `spec.md` нет (MEDIUM без полного spec-kit) — H1 сверяет
   против `goal`/`doneWhen` из `pipeline-state.json`. У спека-adherence всегда есть источник.
2. **Позиция судьи в цепочке гейтов:** судья = **последний гейт перед «done»**, ПОСЛЕ того как
   `/pipeline` closeout прошёл (это и есть H0). НЕ дублирует harness-gates/verify-gate/UI-gate из
   `/pipeline`, а добавляет H1/H2 + S1-S4 поверх. Если closeout не прошёл — судья не зовётся.
3. **`/elt-code` без состояния (первый запуск на проекте):** нет `pipeline-state.json` → если проект
   не эталонный, предложить `/project-bootstrap`; иначе сразу свежая классификация через `/pipeline`.
   Не падать на отсутствии state.
4. **Судья в не-Claude:** скил содержит условие — есть механизм субагентов → спавн (Sonnet/Opus); нет
   (Codex/Antigravity) → инлайн в той же сессии. Рубрика и лог `judge_verdict` идентичны.
5. **Критерий «A реализовано» (гейтит старт `/elt-work`):** A считается готовым, когда — (1) все 6
   интентов роутятся; (2) судья отработал live-fire (блок-кейс + совет-кейс) на реальном проекте;
   (3) spec-kit интегрирован ≥1 проекта; (4) зеркало в `~/.codex/skills` проверено; (5) ≥1 реальная
   задача прошла end-to-end через `/elt-code` без трения. Только тогда беремся за `/elt-work`.
6. **Стоимость судьи:** Sonnet-субагент на каждый MEDIUM+ и каждый COMPLEX-слайс — масштабируется со
   слайсами. Приемлемо (Sonnet, не Opus по дефолту), но мониторить на очень длинных COMPLEX.

## Отложено (НЕ в A)
- **(B)** eval-флайвил (измерение + самоулучшение) — после потока реальных прогонов.
- **S5** фронтенд-судья-агент (UI/дизайн-качество) — отдельный per-project агент со своим loadout'ом.
- **security red-team агент** (симуляция атаки) — отдельный специализированный агент.
- **`/elt-work`** (повседневка/компания) — после успешной реализации `/elt-code`.
- **Нативные claude-mem/субагенты в Codex/Antigravity** — крупный R&D, не входит в A.
